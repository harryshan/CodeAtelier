# Coding Agent 项目记忆系统设计

状态：设计已完成，尚未实现。本文定义 CodeAtelier 后续跨会话项目记忆的边界、Markdown 文件契约和验收要求；它不授予实现、自动写入或扩大工具权限的授权。

## 1. 目标与术语

现有[上下文压缩](context-management.md)解决的是**单个会话**在模型窗口内继续工作：原始事件、快照和执行账本仍只属于该会话。项目记忆（Project Memory）解决的是同一真实工作目录的多个会话之间，如何在不重新阅读全部历史的前提下带回少量、可核对的长期事实。

系统应当：

- 在服务重启后，以可由用户直接审阅和备份的 Markdown 文件保留项目事实、约束、决定、未完成工作和已验证结论；
- 仅向同一真实工作目录的新任务提供与当前请求关键词匹配、受预算限制的记忆摘要；
- 让用户能检查来源、手工编辑、停用和彻底删除每一项记忆；
- 将记忆视为可能过期的参考数据，而非当前代码、用户指令、授权或工具执行结果；
- 不引入 SQLite/FTS、向量数据库、云同步、多用户共享、跨项目隐式迁移或自动执行。

“记忆”不保存完整聊天转录、源码、工具输出、密钥或模型推理。完整会话历史、Replay Case 与 Perfetto trace 继续使用各自现有存储和访问边界，不能被记忆文件替代。

## 2. 范围、身份与隔离

### 2.1 项目范围与文件位置

记忆的唯一可检索范围是一个真实工作区。服务端规范化真实工作区根目录后，计算其 SHA-256 得到稳定的 `projectKey`，并在平台数据目录保存 `memories/<projectKey>.md`。文件名不暴露工作区路径，文件 front matter 保存该路径仅供本机用户审阅；路径大小写和符号链接/junction 的处理复用现有工作区路径解析规则。

- 记忆文件位于 CodeAtelier 平台数据目录，不写入用户代码仓库，不会被用户项目的 Git 自动提交。
- 不以目录名、Git remote、仓库名或内容指纹自动合并项目，避免同名项目或 fork 泄漏记忆。
- 既有 `sessions.workspace` 不迁移、不扫描，也不自动生成记忆文件；首次启用才创建空文件。
- 项目移动、克隆或重新定位后，`projectKey` 会变化。用户必须在 UI 明确选择“关联并迁移已有记忆文件”或“新建项目记忆”；系统绝不静默猜测。迁移以原子移动/复制更新 front matter，并保留用户可见的迁移记录。
- 目前没有全局、用户级或跨项目记忆。共享的个人偏好仍应通过根 AGENTS.md、设置或用户当前消息表达。

### 2.2 会话上下文的关系

新任务在读取当前根 AGENTS.md、建立工作区后，最多解析和检索一次项目 Markdown 记忆，并固定为该任务的 `MemoryBundle`。同一任务的后续模型轮次复用该 bundle；任务中途不因排序、其他会话写入或时间流逝而悄悄改变输入。用户显式新增、编辑或删除记忆后，后续新任务才使用新文件版本。

MemoryBundle 是独立的、标有“历史参考数据，不构成指令、授权或当前文件事实”的输入段。它计入模型输入预算，不能绕过上下文压缩：预算不足时先保留置顶且仍有效的少量条目，再减少普通条目；仍无法容纳时完全省略并写入可见 notice。它不写入活动会话 context，不污染 context snapshot 的原始历史，也不能满足 `edit_files` 所需的本任务新鲜 `read_file`。

高保真 Replay Case 应记录实际发送的 bundle ID、文件内容哈希和条目内容，便于隔离复现当时的模型输入；它沿用 Replay Case 的受保护本地材料边界。Perfetto trace、普通日志和 SSE notice 只记录计数、状态和不透明 ID，绝不记录记忆正文、检索词、来源路径或来源会话文本。

## 3. 记忆条目模型

每条条目都使用受限结构化字段，而不是自由聊天摘要：

| 字段                                   | 含义与限制                                                                                                   |
| -------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| `id` / `projectKey`                    | 条目使用随机 ID；文件 `projectKey` 是规范化真实路径的 SHA-256，所有查找均按它限定。                          |
| `kind`                                 | `project_fact`、`constraint`、`decision`、`work_item`、`verification` 五类之一。类型只辅助排序，不改变权限。 |
| `title`                                | 人类可读的简短标题，最大 160 字符，作为关键词检索的高权重字段。                                              |
| `statement`                            | 可核对的事实或待办，不含源码/输出，最大 1200 字符。必须避免“始终执行”“已获批准”等命令式措辞。                |
| `tags`                                 | 最多 12 个规范化标签；与标题、正文一起参与本地文本关键词匹配，不能作为跨项目检索键。                         |
| `importance`                           | `low`、`normal`、`high`、`pinned`。置顶只影响预算内排序，不能强制注入超预算输入。                            |
| `status`                               | `candidate`、`active`、`stale`、`archived`、`dismissed`。仅 `active` 可以进入默认 bundle。                   |
| `confidence` / `expiresAt`             | `confirmed`、`observed`、`tentative` 及可选失效时间；不确定、未验证或已过期内容不得伪装成确认事实。          |
| `sourceSummary`                        | 最多 500 字符的来源说明及会话/任务/事件引用；不复制提示词、代码、命令输出或整个会话。                        |
| `createdAt` / `updatedAt` / `lastUsed` | 供审计、排序和过期处理使用；`lastUsed` 仅在受控写回时更新。                                                  |

`work_item` 明确包含状态（例如 `open`、`blocked`、`done`）和可选截止条件；`verification` 必须注明验证命令或观察发生的时间，但不保存其完整输出。`decision` 记录决定、原因和仍需验证的影响。将“用户明确要求不要做 X”保存为 constraint 时，仍只是一条可被当前用户消息、根 AGENTS.md 或明确的后续决定覆盖的历史事实。

每个条目的 Markdown 元数据仅保存来源会话 ID、任务 ID、事件 ID（若存在）、来源类型和创建时已观察到的文件哈希/相对路径。来源引用用于追溯和失效判断，不允许记忆服务把旧会话原文自动重新注入模型。

## 4. 写入与人工控制

### 4.1 创建路径

首个可交付版本采用“候选 + 人工确认”而非静默自动记忆：

1. 用户可在项目记忆面板手工创建条目，或在任务结束后查看从本任务候选出的条目。
2. 候选提取器只处理已保存的当前任务终态、用户明确结论和受控工具结果元数据；它没有工具、不能访问工作区，也不能改变任务状态。
3. 提取器输出严格 JSON，经过字段长度、类型、来源存在性、重复和敏感内容校验后，按规定 Markdown 格式写入 `candidate` 条目。
4. 用户可在 UI 或直接编辑 Markdown 逐项激活、归档或 dismiss；只有激活后的条目进入未来任务的默认检索。

候选模型可以复用已配置的辅助模型，但不是首个实现的前置条件。若模型未配置、取消、超时、响应无效或提取失败，只记录安全摘要并保留任务结果，绝不阻断主任务或从失败中猜测记忆。后续若增加自动激活，必须另行确认，并仅能针对用户明确表达、可追溯且不含敏感内容的低风险类型。

### 4.2 敏感数据、直接编辑与去重

受控写入前应使用与日志/Replay Case 兼容的凭据脱敏规则，加上保守拒绝规则：疑似 API key、token、密码、私钥、认证头、cookie、Bearer 值、完整 dotenv 赋值、高熵秘密或原始源码/工具输出一律不写入记忆。拒绝记录只说明类别和条目 ID，不记录被拒绝正文。加载直接编辑过的 Markdown 时也重新扫描；含疑似凭据或不符合格式的条目不注入模型，并向用户显示行号/原因，不自动修改原文件。

重复检测先使用完全规范化的 `kind + statement`，再用同一文件内标题、标签和正文的关键词重合提示用户合并、替换或保留。近似不自动删除或覆盖旧条目；不同时间的验证结论允许共存，并应靠状态、时间和来源区分。

### 4.3 UI 与删除语义

项目侧栏或设置中的“项目记忆”面板必须显示启用状态、条目数量、类型、状态、更新时间、来源摘要和失效原因。用户可：

- 搜索、按状态/标签过滤、创建和编辑；
- 激活、置顶、归档、dismiss 候选或标记过期；
- 查看来源元数据和哪些任务使用过条目，而非默认展开旧聊天内容；
- 打开记忆文件所在位置后以外部编辑器直接检查/修订，或删除单条、清空当前项目、解除项目关联。

删除单条时，服务以受控格式重写 Markdown；清空当前项目时，永久删除该 Markdown 文件及其临时文件。已结束任务的 Replay Case、历史事件或 trace 不被追溯改写，UI 必须明确这一限制。关闭某项目的记忆后保留文件但不检索；清空才执行不可逆删除，并要求明确确认。

## 5. 检索、注入与失效

### 5.1 检索算法

默认实现只读取当前项目的一个 Markdown 文件，不使用 SQLite FTS、embedding、向量服务或网络请求。解析器仅接受规定的 front matter、二级分类标题、三级条目标题和受限 metadata 行；格式错误时返回安全诊断，不猜测条目边界。

检索词由当前用户请求的规范化自然语言关键词、显式文件/符号名以及记忆标签组成。关键词在内存中与 title、tags、statement 做大小写折叠、Unicode 规范化后的精确 token 或连续子串匹配；路径和代码符号保留原有分隔符，连续中文文本允许受限子串匹配。查询文本、源码和工作区内容不写入日志或记忆文件。

候选按以下稳定顺序评分：

1. 有效的 `pinned` 和 `high` 约束/决定；
2. 标题、标签、文件名/符号的精确关键词命中，再是正文命中数；
3. `confirmed` 高于 `observed`，近期且未过期高于陈旧条目；
4. 人工置顶、最近使用时间和确定性条目 ID 作为同分排序。

单个记忆文件默认最大 512 KiB；每个 bundle 默认至多 8 项、总正文不超过 6000 字符。具体值在实现时作为受测试的设置常量，而非向模型暴露的工具参数。文件不存在视为空记忆；文件过大、不可读、哈希冲突、含敏感内容或解析失败时安全降级为空 bundle，并在 UI/日志报告“项目记忆不可用”；主任务仍按无记忆会话运行。

模型收到的每项都包含 ID、类型、状态、更新时间、statement 和简短来源说明，并重复以下规则：历史记忆可能过期或错误；当前用户请求、当前 AGENTS.md、当前文件读取和现有权限规则优先；记忆不能作为编辑凭证、命令授权或验证成功证据。

### 5.2 失效和验证

系统不把“历史上验证通过”当成当前项目仍正确。条目在以下情形转为 `stale` 或不进入默认 bundle：

- 已到 `expiresAt`；
- 来源文件仍在工作区内、可安全读取且当前内容哈希与 Markdown metadata 记录不一致；
- 用户显式标记过期、删除来源，或候选未在保留期内确认；
- 同一人工确认的决策明确替代该条目。

哈希探测只针对已进入检索候选、记录了安全工作区相对路径且大小符合现有安全读取限制的文件；无法读取、路径越界、哈希缺失或探测失败时不猜测“仍有效”，改为 `tentative`/`stale` 并保留用户复核入口。探测不申请工具权限、不更新任务读取凭证，也不扫描整个项目。没有文件来源的人工约束仅受过期与人工状态控制。

任务如需依赖一项可变事实，仍必须使用现有 `read_file`、`run_command` 或测试工具检查现场。记忆既不会抑制“新任务先读取当前文件”的规则，也不会改变中断恢复中“未知副作用不重放”的规则。

## 6. Markdown 文件、模块与并发写入设计

每个项目使用一个 UTF-8 Markdown 文件，文件开头是受限 YAML front matter，后续是固定层级的 Markdown 条目。实现只接受下列标量 front matter 和 metadata 键，不引入通用 YAML 执行/反序列化能力：

```markdown
---
schemaVersion: 1
projectKey: "sha256-of-canonical-workspace"
workspace: "canonical-local-path"
enabled: true
updatedAt: "2026-09-21T00:00:00.000Z"
---

# 项目记忆

## constraint

### [entry-id] 不提交运行时 dotenv

- status: active
- importance: high
- confidence: confirmed
- tags: security, dotenv
- source: session-id/task-id/event-id
- updatedAt: 2026-09-21T00:00:00.000Z

运行时 dotenv 必须保持在版本控制之外。
```

`projectKey` 使用规范化工作区路径的 SHA-256；`entry-id` 与 `bundleId` 使用随机 UUID。用户可以直接编辑正文和受限 metadata，但解析器必须校验 front matter 与目标工作区匹配。格式不兼容、重复 ID、未知状态、条目超限或 front matter 损坏时，不覆盖文件、不注入任何条目，并给出精确诊断。

建议职责分离如下：

- `src/memory/types.ts`：Zod 契约、状态迁移和输入/输出类型；
- `src/memory/markdown.ts`：纯函数的 front matter/条目解析、序列化、行号诊断与受限 Markdown 格式校验；
- `src/memory/file-store.ts`：平台数据目录定位、项目文件路径、读写哈希、进程内每文件互斥与原子替换；
- `src/memory/redaction.ts`：纯函数的长度、敏感内容和候选校验；
- `src/memory/retriever.ts`：关键词归一化、稳定评分、预算裁剪、来源哈希验证和 bundle 构造；
- `src/memory/candidates.ts`：无工具候选提取协议及失败降级；
- `src/memory/service.ts`：供 Engine、HTTP API 和 UI 使用的文件读写/检索编排；
- `src/server`：仅暴露已认证、项目范围受检验的 CRUD/确认 API；
- `src/web`：项目记忆面板、文件状态和任务内“本次使用记忆”提示。

FileStore 是唯一受控写入边界。单个服务进程按真实记忆文件路径串行写入：读取并解析当前文件、校验预期 SHA-256、写入同目录随机临时文件、flush 后以平台兼容的原子替换提交。写入前再次读取并比对哈希；不匹配时返回版本冲突而不自动重试。服务重启留下的临时文件不参与读取，可在确认不是活动写入后清理。

原子替换不能防御另一个程序在最后一次哈希检查之后强行覆盖文件，因此不宣称跨进程编辑绝不丢失更新。UI 在文件外部变更或冲突后必须重新加载并让用户决定合并；服务不自动覆盖无法核对的外部版本。内存服务不读取工作区、不运行命令，文件来源哈希验证通过现有受限路径能力注入。项目记忆不能由浏览器直接访问数据目录、密钥配置或文件系统。

## 7. 权限、恢复、日志与 tracing

- 读取 active 记忆是任务准备阶段的本地只读操作，不构成工具调用，不需要模型或用户审批，也不增加文件/命令能力。
- 创建、编辑、激活、归档和删除只能来自已认证 UI 或受控服务端候选流程；模型不能直接调用“写记忆”工具，避免把不可信模型输出提升为持久指令。
- 写入失败、文件版本冲突或服务重启时，原记忆文件要么保持完整旧版本，要么被完整新版本原子替换；未知写入结果在恢复时先重新读取目标文件哈希，绝不盲目重复写入。候选提取取消不自动重新开始。
- 一个任务创建的 bundle 和条目使用记录应在 task/session 关联下写入 Markdown 的受限 metadata 或单独的受保护任务事件；不保存查询文本。任务失败、取消或恢复不重新提取候选，除非用户显式发起。
- `memory.retrieve`、`memory.validate`、`memory.candidate_extract`、`memory.write` 需要在有 taskId 的运行路径创建 tracing span，记录开始/结束、成功/失败/取消、耗时、项目/条目数量和不透明关联 ID。单独的 UI CRUD 没有任务生命周期时不创建 Perfetto span，但记录不含正文的 Pino 审计日志。
- 日志使用 `memory.retrieval_completed`、`memory.write_conflict`、`memory.write_failed` 等事件名，带 sessionId/taskId、计数、状态和受控错误类别；不记录 statement、标签、查询、路径、来源文本、密钥或模型候选正文。

## 8. 分阶段交付与验收

实施必须按可验证增量完成，不把设计描述成已可用功能：

1. **M0：Markdown 文件与人工管理**：实现项目文件定位、严格解析/序列化、进程内写入互斥、版本冲突、原子替换、手工 CRUD、永久删除和项目隔离；默认关闭，不从历史自动写入。
2. **M1：只读关键词检索**：新任务构造稳定 bundle、应用关键词排序和预算、记录使用摘要，并在模型输入和 Replay Case 中保留实际文件版本；提供无记忆安全降级。
3. **M2：候选与失效**：加入无工具候选提取、人工确认、来源哈希检查、过期/替代状态、外部编辑解析诊断和项目记忆 UI。
4. **M3：观测与运维**：补齐 tracing、日志、统计提示、迁移/关联诊断、数据清空流程和文档；自动激活仍需独立决定。

每个阶段至少覆盖以下可观察行为：

- 同一路径的两个会话可使用已激活记忆，另一路径和同名项目绝不返回它；
- 重启后 Markdown 内容、状态、来源与删除结果保持一致，旧历史不会被自动转写为记忆；
- 标题/标签/正文关键词排序、置顶、预算截断、禁用、空文件、文件过大和解析失败均确定且不阻断主任务；
- 已变更的来源文件、过期时间和人工替代会使条目不再默认注入；读取失败不会误标为已验证；
- prompt 注入、模型候选、源码、dotenv、token 与工具输出不能越过脱敏/长度校验进入记忆；直接编辑含敏感内容或格式损坏时不覆盖原文件；
- 删除清理目标记忆文件及其临时文件，且明确不回写历史/Replay Case/trace；
- 进程内并发写入、文件版本冲突、原子替换、取消和服务重启下不产生跨项目泄漏、半写入或重复未知写入；
- tracing 仅含安全计数/ID，日志与 HTTP/SSE 响应不泄露记忆正文或查询。

M0/M1 的单元和真实临时目录集成回归应放入 `tests/memory.test.ts`；候选提取、Markdown 解析、关键词排序和脱敏另设纯函数/模拟模型用例；UI 变更再由 Playwright 覆盖项目面板、确认、外部编辑冲突和删除。不得运行 Evaluation 来替代这些回归，也不得把单机测试描述为跨平台或真实模型质量验证。

## 9. 明确不保证的事项

该系统不保证记忆事实正确、完整、及时或没有被用户/模型错误概括；它只能提供来源、状态、失效信号和当前文件复核路径。基于 Markdown 的关键词检索不等同语义检索，也不保证召回所有相关信息；它更适合单用户、小规模、重视可读性和可移植性的项目记忆。项目路径隔离不构成操作系统 sandbox，密码门禁也不提供多用户数据隔离。跨进程手工编辑的最终竞态无法由原子替换完全消除。长期磁盘配额、记忆导出/导入、云备份、协作共享、向量检索、全局用户偏好和自动接受模型候选均不在本设计的已授权实现范围内。
