# Coding Agent 项目记忆系统设计

状态：M0/M1 核心及任务内模型维护已实现；项目管理 UI、来源失效验证和手工恢复/清空尚未实现。本文定义 CodeAtelier 跨会话项目记忆的边界、Markdown 文件契约和验收要求；实现始终不扩大工作区/命令工具权限。

## 1. 目标与术语

现有[上下文压缩](context-management.md)解决的是**单个会话**在模型窗口内继续工作：原始事件、快照和执行账本仍只属于该会话。项目记忆（Project Memory）解决的是同一真实工作目录的多个会话之间，如何在不重新阅读全部历史的前提下带回少量、可核对的长期事实。

系统应当：

- 在服务重启后，以可由用户直接审阅和备份的 Markdown 文件保留项目事实、约束、决定、未完成工作和已验证结论；
- 仅向同一真实工作目录的新任务提供与当前请求关键词匹配、受预算限制的记忆摘要；
- 让用户能检查来源、手工编辑、停用和彻底删除每一项记忆；
- 将记忆视为可能过期的参考数据，而非当前代码、用户指令、授权或工具执行结果；
- 不引入 SQLite/FTS、向量数据库、云同步、多用户共享、跨项目隐式迁移或工作区/命令自动执行。

“记忆”不保存完整聊天转录、源码、工具输出、密钥或模型推理。完整会话历史、Replay Case 与 Perfetto trace 继续使用各自现有存储和访问边界，不能被记忆文件替代。

## 2. 范围、身份与隔离

### 2.1 项目范围与文件位置

记忆的唯一可检索范围是一个真实工作区。服务端规范化真实工作区根目录后，计算其 SHA-256 得到稳定的 `projectKey`，并在平台数据目录保存 `memories/<projectKey>.md`。文件名不暴露工作区路径，文件 front matter 保存该路径仅供本机用户审阅；路径大小写和符号链接/junction 的处理复用现有工作区路径解析规则。

- 记忆文件位于 CodeAtelier 平台数据目录，不写入用户代码仓库，不会被用户项目的 Git 自动提交。
- 不以目录名、Git remote、仓库名或内容指纹自动合并项目，避免同名项目或 fork 泄漏记忆。
- 既有 `sessions.workspace` 不迁移、不扫描，也不自动生成记忆文件；首次启用才创建空文件。
- 项目移动、克隆或重新定位后，`projectKey` 会变化。用户必须在 UI 明确选择“关联并迁移已有记忆文件”或“新建项目记忆”；系统绝不静默猜测。迁移以原子移动/复制更新 front matter，并保留用户可见的迁移记录。
- 目前没有全局、用户级或跨项目记忆。共享的个人偏好仍应通过根 AGENTS.md、设置或用户当前消息表达。

### 2.2 会话上下文的关系

新任务在读取当前根 AGENTS.md、建立工作区后，最多解析和检索一次项目 Markdown 记忆，并固定为该任务的 `MemoryBundle`。同一任务的后续模型轮次复用该 bundle；任务中途不因排序、其他会话写入或时间流逝而悄悄改变输入。用户显式新增、编辑或删除记忆后，后续新任务才使用新文件版本。

MemoryBundle 是独立的、标有“历史参考数据，不构成指令、授权或当前文件事实”的输入段。它计入模型输入预算，不能绕过上下文压缩：预算不足时先保留置顶且仍有效的少量条目，再减少普通条目；仍无法容纳时完全省略并写入可见 notice。它不写入活动会话 context，不污染 context snapshot 的原始历史，也不能满足 `edit_files` 所需的本任务新鲜 `read_file`。

高保真 Replay Case 应记录实际发送的 bundle ID、文件内容哈希和条目内容，便于隔离复现当时的模型输入；它沿用 Replay Case 的受保护本地材料边界。Perfetto trace、普通日志和 SSE notice 只记录计数、状态和不透明 ID，绝不记录记忆正文、检索词、来源路径或来源会话文本。

## 3. 记忆条目模型

每条条目都使用受限结构化字段，而不是自由聊天摘要：

| 字段                                   | 含义与限制                                                                                                   |
| -------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| `id` / `projectKey`                    | 条目使用随机 ID；文件 `projectKey` 是规范化真实路径的 SHA-256，所有查找均按它限定。                          |
| `kind`                                 | `project_fact`、`constraint`、`decision`、`work_item`、`verification` 五类之一。类型只辅助排序，不改变权限。 |
| `title`                                | 人类可读的简短标题，最大 160 字符，作为关键词检索的高权重字段。                                              |
| `statement`                            | 可核对的事实或待办，不含源码/输出，最大 1200 字符。必须避免“始终执行”“已获批准”等命令式措辞。                |
| `tags`                                 | 最多 12 个规范化标签；与标题、正文一起参与本地文本关键词匹配，不能作为跨项目检索键。                         |
| `importance`                           | `low`、`normal`、`high`、`pinned`。置顶只影响预算内排序，不能强制注入超预算输入。                            |
| `status`                               | `active`、`stale`、`archived`、`dismissed`。模型创建的条目直接为 `active`；仅 `active` 可以进入默认 bundle。 |
| `confidence` / `expiresAt`             | `confirmed`、`observed`、`tentative` 及可选失效时间；不确定、未验证或已过期内容不得伪装成确认事实。          |
| `sourceSummary`                        | 最多 500 字符的来源说明及会话/任务/事件引用；不复制提示词、代码、命令输出或整个会话。                        |
| `createdAt` / `updatedAt` / `lastUsed` | 供审计、排序和过期处理使用；`lastUsed` 仅在受控写回时更新。                                                  |

`work_item` 明确包含状态（例如 `open`、`blocked`、`done`）和可选截止条件；`verification` 必须注明验证命令或观察发生的时间，但不保存其完整输出。`decision` 记录决定、原因和仍需验证的影响。将“用户明确要求不要做 X”保存为 constraint 时，仍只是一条可被当前用户消息、根 AGENTS.md 或明确的后续决定覆盖的历史事实。

每个条目的 Markdown 元数据仅保存来源会话 ID、任务 ID、事件 ID（若存在）、来源类型和创建时已观察到的文件哈希/相对路径。来源引用用于追溯和失效判断，不允许记忆服务把旧会话原文自动重新注入模型。

## 4. 写入与用户可见性

### 4.1 模型自主维护路径

模型通过受控的 `memory_apply` 工具在当前任务内自行决定是否创建、更新或清除项目记忆，不显示人工确认卡片，也不等待用户激活。模型在任务过程中自然判断，不要求每个任务结束时都强制复盘是否写入。工具只接受结构化操作，服务端而非模型负责读取、解析和重写 Markdown：

1. 当有充分证据表明信息在未来独立任务中仍有价值时，模型可保存项目特有的稳定约束（工具、版本、风格、安全或运维规则）、已确认的架构/接口/行为/兼容性决定及其理由、已验证的环境支持或限制、明确下一步的待办/阻塞项，以及有可追溯来源的非显然重复陷阱或修复经验。
2. 不保存日常进度、一次性排查细节、瞬态命令或构建输出、未经验证的猜测、重复事实、完整源码或工具输出、敏感数据，以及只对当前对话有用的内容。当前用户请求、当前 AGENTS.md、当前文件读取和权限规则始终优先于记忆。
3. 新证据使旧条目过期、完成、重复或不再相关时，模型可更新或 `archive` 该条目。`archive` 会停止后续检索但保留 Markdown 记录，用户仍可恢复；模型不能永久删除整个项目记忆或任意 Markdown 段落。
4. 每次调用最多 16 个操作：`create` 创建为 `active`，`update` 修改已知条目。每项必须带简短理由和同项目来源会话/任务/事件引用；涉及文件事实时还必须带当前任务观察到的相对路径及内容哈希。
5. 记忆参考始终给出当前版本；空记忆以 `null` 表示。模型用该精确值作为 `expectedVersion`。`memory_apply` 成功时返回当前项目的不透明键、提交后的文件版本和已应用条目 ID；冲突时只允许在下一任务读取刷新后的参考后重新决定，服务不会盲目重放。

模型输出是有来源的建议，服务端将其当作不可信数据校验，而不是权限授予。工具只允许任务绑定的 `projectKey`，不能引用另一个项目、伪造当前任务/会话标识、修改 front matter 或写入未声明字段；同一任务中的并发调用仍由 FileStore 串行化。`memory_apply` 的成功、拒绝或冲突不阻断主任务的用户可见完成结果。

### 4.2 敏感数据、直接编辑与去重

受控写入前应使用与日志/Replay Case 兼容的凭据脱敏规则，加上保守拒绝规则：疑似 API key、token、密码、私钥、认证头、cookie、Bearer 值、完整 dotenv 赋值、高熵秘密或原始源码/工具输出一律不写入记忆。拒绝记录只说明类别和条目 ID，不记录被拒绝正文。加载直接编辑过的 Markdown 时也重新扫描；含疑似凭据或不符合格式的条目不注入模型，并向用户显示行号/原因，不自动修改原文件。

模型创建时，重复检测先使用完全规范化的 `kind + statement`，再用同一文件内标题、标签和正文的关键词重合自动选择更新现有条目、归档旧条目或保留并存。不同时间的验证结论允许共存，并应靠状态、时间和来源区分；服务不会因近似命中擅自删除条目。

### 4.3 UI 与删除语义

项目侧栏或设置中的“项目记忆”面板必须显示启用状态、条目数量、类型、状态、更新时间、来源摘要、失效原因及“由模型自动维护”的状态。用户可：

- 搜索、按状态/标签过滤、创建和编辑；
- 查看模型创建、更新和归档的任务来源与理由，恢复归档条目或手工调整状态；
- 查看来源元数据和哪些任务使用过条目，而非默认展开旧聊天内容；
- 打开记忆文件所在位置后以外部编辑器直接检查/修订，或删除单条、清空当前项目、解除项目关联。

模型 archive 条目时不需要人工确认。单条手工删除时，服务以受控格式重写 Markdown；清空当前项目时，永久删除该 Markdown 文件及其临时文件。已结束任务的 Replay Case、历史事件或 trace 不被追溯改写，UI 必须明确这一限制。关闭某项目的记忆后保留文件但不检索；清空才执行不可逆删除，并要求明确确认。

## 5. 检索、注入与失效

### 5.1 检索算法

默认实现只读取当前项目的一个 Markdown 文件，不使用 SQLite FTS、embedding、向量服务或网络请求。解析器仅接受规定的 front matter、二级分类标题、三级条目标题和受限 metadata 行；格式错误时返回安全诊断，不猜测条目边界。

检索词由当前用户请求的规范化自然语言关键词、显式文件/符号名以及记忆标签组成。关键词在内存中与 title、tags、statement 做大小写折叠、Unicode 规范化后的精确 token 或连续子串匹配；路径和代码符号保留原有分隔符，连续中文文本允许受限子串匹配。查询文本、源码和工作区内容不写入日志或记忆文件。

候选按以下稳定顺序评分：

1. 有效的 `pinned` 和 `high` 约束/决定；
2. 标题、标签、文件名/符号的精确关键词命中，再是正文命中数；
3. `confirmed` 高于 `observed`，近期且未过期高于陈旧条目；
4. 人工置顶、最近使用时间和确定性条目 ID 作为同分排序。

单个记忆文件默认最大 512 KiB；每个 bundle 默认至多 8 项、总正文不超过 6000 字符。具体值作为受测试的实现常量，而非向模型暴露的工具参数。文件不存在视为空记忆；文件过大、不可读、含敏感内容或解析失败时安全降级为不可用且不注入 bundle，并记录受控日志与任务 notice；主任务仍按无记忆会话运行。

模型收到的每项都包含 ID、类型、状态、更新时间、statement 和简短来源说明，并重复以下规则：历史记忆可能过期或错误；当前用户请求、当前 AGENTS.md、当前文件读取和现有权限规则优先；记忆不能作为编辑凭证、命令授权或验证成功证据。

### 5.2 失效和验证

系统不把“历史上验证通过”当成当前项目仍正确。条目在以下情形转为 `stale` 或不进入默认 bundle：

- 已到 `expiresAt`；
- 来源文件仍在工作区内、可安全读取且当前内容哈希与 Markdown metadata 记录不一致；
- 用户显式标记过期、删除来源，或模型依据当前任务证据 archive 该条目；
- 同一用户或模型记录的后续决策明确替代该条目。

哈希探测只针对已进入检索候选、记录了安全工作区相对路径且大小符合现有安全读取限制的文件；无法读取、路径越界、哈希缺失或探测失败时不猜测“仍有效”，改为 `tentative`/`stale` 并保留用户复核入口。探测不申请工具权限、不更新任务读取凭证，也不扫描整个项目。没有文件来源的用户创建约束仅受过期与用户或模型状态控制。

任务如需依赖一项可变事实，仍必须使用现有 `read_file`、`run_command` 或测试工具检查现场。记忆既不会抑制“新任务先读取当前文件”的规则，也不会改变中断恢复中“未知副作用不重放”的规则。

## 6. Markdown 文件、模块与并发写入设计

每个项目使用一个 UTF-8 Markdown 文件，文件开头是受限 YAML front matter，后续是固定层级的 Markdown 条目。实现只接受下列标量 front matter 和 metadata 键，不引入通用 YAML 执行/反序列化能力：

```markdown
---
schemaVersion: 1
projectKey: "sha256-of-canonical-workspace"
workspace: "canonical-local-path"
enabled: true
updatedAt: "2026-09-21T00:00:00.000Z"
---

# 项目记忆

## constraint

### [entry-id] 不提交运行时 dotenv

- status: active
- importance: high
- confidence: confirmed
- tags: security, dotenv
- source: session-id/task-id/event-id
- updatedAt: 2026-09-21T00:00:00.000Z

运行时 dotenv 必须保持在版本控制之外。
```

`projectKey` 使用规范化工作区路径的 SHA-256；`entry-id` 与 `bundleId` 使用随机 UUID。用户可以直接编辑正文和受限 metadata，但解析器必须校验 front matter 与目标工作区匹配。格式不兼容、重复 ID、未知状态、条目超限或 front matter 损坏时，不覆盖文件、不注入任何条目，并给出精确诊断。

建议职责分离如下：

- `src/memory/types.ts`：Zod 契约、状态迁移、`memory_apply` 输入/输出类型及每项操作上限；
- `src/memory/markdown.ts`：纯函数的 front matter/条目解析、序列化、行号诊断与受限 Markdown 格式校验；
- `src/memory/file-store.ts`：平台数据目录定位、项目文件路径、读写哈希、进程内每文件互斥与原子替换；
- `src/memory/redaction.ts`：纯函数的长度、敏感内容和模型记忆操作校验；
- `src/memory/retriever.ts`：关键词归一化、稳定评分、预算裁剪、active/过期过滤和 bundle 构造；
- `src/memory/mutator.ts`：按当前任务/项目验证 create、update、archive，处理去重和版本冲突；
- `src/memory/service.ts`：供 Engine、工具调度、HTTP API 和 UI 使用的文件读写/检索编排；
- `src/tools`：将 `memory_apply` 注册为参数受限的模型工具，不提供任意文件写入或项目级物理删除；
- `src/server`：仅暴露已认证、项目范围受检验的查看、恢复和手工清空 API；
- `src/web`：项目记忆面板、模型维护来源、文件状态和任务内“本次使用记忆”提示。

FileStore 是唯一受控写入边界。单个服务进程按真实记忆文件路径串行写入：读取并解析当前文件、校验预期 SHA-256、写入同目录随机临时文件、flush 后以平台兼容的原子替换提交。写入前再次读取并比对哈希；不匹配时返回版本冲突而不自动重试。服务重启留下的临时文件不参与读取，可在确认不是活动写入后清理。

原子替换不能防御另一个程序在最后一次哈希检查之后强行覆盖文件，因此不宣称跨进程编辑绝不丢失更新。UI 在文件外部变更或冲突后必须重新加载并让用户决定合并；服务不自动覆盖无法核对的外部版本。内存服务不读取工作区、不运行命令，文件来源哈希验证通过现有受限路径能力注入。项目记忆不能由浏览器直接访问数据目录、密钥配置或文件系统。

## 7. 权限、恢复、日志与 tracing

- 读取 active 记忆是任务准备阶段的本地只读操作，不构成工具调用，不需要模型或用户审批，也不增加文件/命令能力。
- 模型可在当前任务调用参数受限的 `memory_apply`，自动创建、更新和 archive 同项目条目，不请求人工确认。该能力只修改平台数据目录中当前项目的记忆文件，不能修改工作区、权限规则、AGENTS.md、会话历史或任意路径。
- 写入失败、文件版本冲突或服务重启时，原记忆文件要么保持完整旧版本，要么被完整新版本原子替换；未知写入结果在恢复时先重新读取目标文件哈希，绝不盲目重复写入。未完成或结果未知的 `memory_apply` 不自动重放，恢复后的模型需要重新读取记忆状态再决定。
- 一个任务创建的 bundle 和每次模型变更的操作摘要应在 task/session 关联下写入 Markdown 的受限 metadata 或单独的受保护任务事件；不保存查询文本、模型原始响应或条目正文。任务失败、取消或恢复不自动生成新的记忆操作，除非恢复后的模型显式调用工具。
- `memory.retrieve`、`memory.apply` 需要在有 taskId 的运行路径创建 tracing span，记录开始/结束、成功/失败/取消、耗时和安全的操作计数。单独的 UI CRUD 没有任务生命周期时不创建 Perfetto span，但记录不含正文的 Pino 审计日志。
- 日志使用 `memory.retrieval_completed`、`memory.apply_completed`、`memory.write_conflict`、`memory.apply_failed` 等事件名，带 sessionId/taskId、计数、状态和受控错误类别；不记录 statement、标签、查询、路径、来源文本、密钥或模型候选正文。

## 8. 分阶段交付与验收

已按可验证增量交付以下范围，剩余项不能描述为已可用功能：

1. **已完成 M0 核心**：项目文件定位、严格解析/序列化、进程内写入互斥、版本冲突、原子替换、`memory_apply` 参数校验、自动 create/update/archive 和项目隔离；不从历史自动写入，也不提供任意 Markdown 写入或项目级物理删除。
2. **已完成 M1 核心**：每个任务开始时构造固定 bundle，按本地关键词排序和预算裁剪后注入模型指令；文件不存在为空记忆，文件损坏时主任务按无记忆继续。
3. **已完成的可观察性**：任务内 `memory.retrieve` 与 `memory.apply` span 不含正文或工具参数；Pino 日志仅保存计数、状态和受控错误类别，任务事件仅保存可用状态、条目数量或操作数量，工具结果向模型返回版本及操作 ID。
4. **后续 M2/M3**：来源哈希失效验证、外部编辑诊断、项目记忆 UI、手工恢复/清空、迁移/关联诊断、统计提示和模型维护质量评估另行实现与验证。

每个阶段至少覆盖以下可观察行为：

- 同一路径的两个会话可使用已激活记忆，另一路径和同名项目绝不返回它；
- 重启后 Markdown 内容、状态、来源与模型 archive 结果保持一致，旧历史不会被自动转写为记忆；
- 标题/标签/正文关键词排序、置顶、预算截断、禁用、空文件、文件过大和解析失败均确定且不阻断主任务；
- 模型在同一任务内可以无需人工确认地创建、更新、归档条目；跨项目、未知条目 ID、超量操作、无来源、任意 Markdown 写入和项目级物理删除均被拒绝；
- 已变更的来源文件、过期时间和模型/人工替代会使条目不再默认注入；读取失败不会误标为已验证；
- prompt 注入、模型操作、源码、dotenv、token 与工具输出不能越过脱敏/长度校验进入记忆；直接编辑含敏感内容或格式损坏时不覆盖原文件；
- archive 从检索中清除但允许恢复；手工永久清空清理目标记忆文件及其临时文件，且明确不回写历史/Replay Case/trace；
- 进程内并发写入、文件版本冲突、原子替换、取消和服务重启下不产生跨项目泄漏、半写入或重复未知写入；
- tracing 仅含安全计数/ID，日志与 HTTP/SSE 响应不泄露记忆正文或查询。

M0/M1 的单元和真实临时目录集成回归放在 `tests/memory.test.ts`；`memory_apply` 契约及 Engine 模型工具接入由 `tests/tool-schema.test.ts`、`tests/engine.test.ts` 覆盖。来源哈希失效、恢复未知结果、项目面板、外部编辑冲突和手工清空待对应功能实现后补充测试。不得运行 Evaluation 来替代这些回归，也不得把单机测试描述为跨平台或真实模型质量验证。

## 9. 明确不保证的事项

该系统不保证记忆事实正确、完整、及时或没有被模型错误概括、错误归档；它只能提供来源、状态、失效信号、模型操作记录和当前文件复核路径。模型自动 archive 不等同于事实已失效，用户可从 Markdown/UI 恢复。基于 Markdown 的关键词检索不等同语义检索，也不保证召回所有相关信息；它更适合单用户、小规模、重视可读性和可移植性的项目记忆。项目路径隔离不构成操作系统 sandbox，密码门禁也不提供多用户数据隔离。跨进程手工编辑的最终竞态无法由原子替换完全消除。长期磁盘配额、记忆导出/导入、云备份、协作共享、向量检索、全局用户偏好、模型任意文件写入和模型项目级物理删除均不在本设计的已授权实现范围内。
