### Local overlay 目标重新澄清（2026-10-25，D170）

用户要求 Overlay 与 Git worktree 完全并列：Overlay 用于同一 Local 工作区多个对话的文件修改隔离与冲突整合，不负责 Git 分支、提交、index 或对象库管理。此前 D169 的 Git 提交虚拟 worktree 实验不再作为这个需求的后续方向。普通 Worktree 保留原有 Git 工作流；用户追加授权完整验证、自审后接入 agent，并确认每轮成功后自动发布明确选择的源码变更，冲突/验证失败保留私有修改。Windows 沿用自研 WinFsp 后端；LayerFS 调查后不采用。Local 挂载策略、真实 Sandbox 并行/取消/续聊，以及原生自动基线/冻结导出和 Windows owner/group/DACL 保留发布的 PoC 已验证，新路径不依赖 Riftri/Git 注册；成功发布后的确认/刷新已有 Windows PoC；恢复操作和产品生命周期仍待接入，不自动迁移旧会话。选型、实时读取、编辑基线、串行发布与冲突恢复的边界和证据见 [Local overlay 设计](local-overlay-design.md)。

## 2. 初版功能边界（已确认）

目标：在本机浏览器中，通过对话完成一个本地项目的代码阅读、修改和验证，并保存历史对话。

| 范围     | 初版包含                                                                                                                      |
| -------- | ----------------------------------------------------------------------------------------------------------------------------- |
| 项目     | 输入或选择本机项目目录；每个会话绑定一个项目，同一项目可建立多个独立对话；UI 按项目分组，项目名称右侧的加号直接建立项目内对话 |
| 对话     | 多轮交流、流式回复、新建与续聊；历史和过程可展开查看                                                                          |
| 理解代码 | 通过受审批的 `run_command` 使用本机命令列目录、搜索文件名与代码内容；按行读取文件；读取项目 AGENTS.md                         |
| 网页检索 | 通过 Responses 内置 `web_search` 查询公开网页并显示可点击来源；搜索摘要不足时可在既有权限边界内用 `curl` 获取网页正文         |
| 修改代码 | 通过统一 `edit_files` 批量新建文件或精确修改已有文件、展示修改 diff                                                           |
| 执行验证 | 执行构建、测试等命令，展示输出和退出状态                                                                                      |
| Git 操作 | 通过 Git CLI 查看状态、差异、历史及分支，执行暂存、提交和推送；按通用命令权限执行，不自动校验 upstream 或限制 Git action      |
| 权限     | 工作区内普通修改自动执行；危险操作和外部写入需确认，后端落实权限检查                                                          |
| 执行控制 | 展示工具执行过程、取消任务、超时与步数限制、明确报告失败                                                                      |
| 模型配置 | 配置 API 地址、密钥、模型和思考等级（默认 high），首个协议为 Responses，对接用户自建服务                                      |
| 历史保存 | 本地保存消息、工具调用及结果；浏览器关闭或服务重启后可查看                                                                    |
| 平台     | Windows、macOS、Linux；Web UI 与后端默认仅本机访问，可显式开放受信任局域网                                                    |

### 设置系统重设计（2026-10-16，D153）

用户要求把大部分环境配置移至 `settings.json`，可以随时配置，完整重新设计配置 UI，最终移除 `.env`。目标替代 R9/R13、D065/D073/D152 中相应的环境配置来源约束，不改变模型协议、审批、隔离和历史恢复边界。产品启动已切换到版本化文件，遗留环境解析仅用于显式迁移和兼容夹具。

版本化文件、私有凭据存储、任务快照、分级生效、首次引导、设置 API/分类 UI 与离线迁移器已接入；具体操作及验证边界见 [设置系统](settings-system.md)。本轮不搬动真实凭据、不删除真实 `.env`、不重启当前服务。

### 第一批多协议模型支持（2026-10-16）

2026-10-18 用户追加要求先实现 Responses `prompt_cache_key`（D160）：主任务按会话稳定绑定，subagent 按会话/任务/子任务身份分别绑定；宿主和 Broker 使用同一规则。无新配置、权限或 IPC 字段，不保证上游缓存命中；参数及诊断边界见 [模型协议](model-protocols.md#responses-prompt-cache-key)。

用户授权保留 Responses，新增 OpenAI Chat Completions 与 Anthropic Messages。主任务、辅助标题/摘要、审批和 Broker 模型代理按统一工厂选择协议；主/辅助可独立配置协议、地址、模型与密钥。默认仍为 Responses，连接由设置页编辑并存入私有文件，不改变既有审批或恢复语义。

新增协议首批支持文字流、多函数调用与结果往返、取消/时限、错误和 usage；暂不接入思考扩展、原生搜索或多模态。不兼容历史明确拒绝，不丢弃不透明内容、不改写已有数据库；跨协议任意历史切换不在本批验收范围。配置、兼容边界和验证见 [模型协议](model-protocols.md)（D152）。

### 追加 MCP 范围（2026-10-03）

用户要求实现 MCP，并确认由本机后端连接本地 stdio 或远程 MCP 服务，不使用模型服务商托管连接。通过普通 `mcp` 工具发现/调用服务工具，读取资源和查询提示模板；本地配置、凭据、审批与连接生命周期由后端管理。宿主与 Sandbox Runtime 经 Broker 使用相同接口，结果标记 `broker-mcp/host-process`，不宣称受 Sandbox 保护。每次主任务开始时主动提供已启用服务的名称、配置用途描述和 transport，模型可按任务需要直接发现对应服务的工具；摘要不包含连接配置、不提前连接或授予权限。旧配置未填写 description 时明确标注用途未知。没有配置时提供空目录且不创建连接；历史、失败、取消、输出限制与未知结果不重放规则照常生效。具体配置、协议能力和验收限制见 [MCP 支持](mcp.md)。

### 追加 Skill 范围（2026-10-03）

用户要求实现 Skill，自动加载几个预设目录并向模型提供调用接口。当前每主任务扫描项目及宿主用户的 `.codeatelier/skills`、`.agents/skills`、`.claude/skills`，自动提供有效 `SKILL.md` 的名称/用途，正文经 `skill list/load` 按需读取。项目优先、同名固定优先级，坏条目隔离，后续任务刷新；不自动执行脚本，不将技能内容或元信息视为授权。宿主与 Runtime 共用 Broker 目录及读取接口，边界和格式见 [Skill 指南](skills.md)。这不扩展为插件市场或任意宿主文件读取能力。

### 对话交互

- 对于需要多步骤调查、跨文件修改或验证的复杂任务，agent 先读取相关代码和文件并获得足够信息，再自行显示简洁的计划摘要并立即按计划执行，必要时说明实质调整。
- 所有已结束任务（正常完成、失败、取消、中断）的中间过程默认折叠，可按需展开；用户输入、已有的最后一条完整 agent 回复、中断提示与恢复入口保持可见。排队、运行和等待审批的任务保持完整显示。
- 打开历史对话后可直接连续滚动查看全部以往记录，无需点击“查看更早”翻页；接近顶部自动加载旧记录并保持阅读位置。底层仍分页和虚拟渲染，不要求一次下载全量历史；读取失败可重试，浏览历史时新消息不抢滚动位置。
- 任务输入框是所见即所得 Markdown 编辑器，输入规则原地转换为富文本并将生成的 Markdown 提交。
- 用户与 agent 消息以安全的 GitHub Flavored Markdown 显示，不执行原始 HTML。
- subagent 状态按主任务和子任务合并为一条原位更新的最新状态，不逐条展示重复的“调查中”；工具审批保留结论与理由，不再单独展示审批模型用量卡片。完整事件和统计不删减，人工审批按钮及执行权限不变。
- 当前会话在对话角落提供默认折叠的本地统计，可展开查看服务实报 token、LLM 请求/轮次、工具调用与成功率、任务数量和累计运行时间。
- 2026-10-05 用户追加要求改善导出 JSON 的阅读，并明确由现有 Web 服务提供阅读器，无需生成独立 HTML。主界面入口及 `/?view=replay` 复用访问密码门禁，按模型请求查看关联工具、参数/结果与事件，支持搜索、状态筛选和分页；用户进一步要求直接浏览当前数据库的对话与 Task：默认通过后端只读接口选择已有记录，无需导出；校验归属与访问凭据，支持刷新及 URL 选择恢复，不重放任务。浏览器本地 JSON 与旧单文件导出仅为兼容选项，见 [Replay Case](replay-cases.md#可视化阅读)（D132、D133、D134）。2026-10-13 用户明确要求恢复原版分类阅读器：按轮次、模型、工具及历史事件分类，不平铺整个时间线，不增加手动加载 Task/请求的按钮；保留搜索、状态筛选、关联跳转及原版本地目录导航，不回退数据库迁移。

### 执行限制

- 长时间工具操作不设置固定总运行时限。命令、Broker 命令、Git 及 MCP 操作实际开始后，每五分钟把最新有界输出与运行状态交主模型判断继续等待或中断本次调用；复查失败继续等待，用户取消始终有效。等待不能重放工具，停止不撤销既有副作用。连接建立、模型请求和取消清理的独立安全期限保留，详见 [长工具运行](long-running-tools.md)（D141）。

- 默认单 agent；2026-10-17 用户要求开放可选 subagent 的 UI 任务级开关（D158）。开关默认关闭、仅本次提交生效、成功发送后复位；运行和排队期间不可切换，人工恢复沿用来源任务选择。入口开放不代表所有平台及安装态专项验收通过。不同真实工作目录的会话可并行执行，默认最多 2 个、设置可调为 1～4 个；同一工作目录始终只运行一个主任务，后续任务保持排队。一个会话仍只允许一个运行中或排队中的主任务，避免并发追加其上下文。
- 用户于 2026-10-03 要求移除 subagent 专属研究配额：不再限制提问/消息次数、子模型轮数、独立运行时长、累计 token、文本与上下文大小、累计创建数量；保留活动 Worker 并发调度、只读权限、取消/恢复及共享传输/模型物理容量边界，入口开放由 D158 另行决定。2026-10-18 用户明确 subagent 也须遵循设置中的最大输出 token：两角色每轮继承当前任务配置及已知模型容量约束，不恢复旧固定 2,048 token 配额。完整清单见 [多 agent 设计](multi-agent-design.md)。
- 2026-10-17 用户要求两种内置 subagent：`explorer` 获取并筛选信息后交回主 agent；`reviewer` 用干净上下文审查主 agent 修改。两种角色均可多开，在不同范围内并行；沿用共享活动 Worker 调度与只读边界，UI 开放按 D158。reviewer 接收明确的变更材料，不自动继承父对话或同伴报告，详见 [多 agent 设计](multi-agent-design.md)（D157）。
- 2026-10-17 用户追加要求向 subagent 暴露 `web_search`（D159）：explorer/reviewer 在 Responses 协议下均可使用模型服务内置公开搜索，Chat Completions / Messages 不声明。沿用来源引用、模型历史、取消和恢复，不开放子任务 shell、任意网络命令或写入权限。
- D167：新对话默认 Riftri 原生 CoW，以主目录当前状态创建独立目录，包含脏文件、暂存区、未跟踪和忽略文件，不选择 commit/branch、不另建 base、不做 blob hash 校验。普通 Git worktree 并列且须显式选择，保留指定提交的干净基线。Riftri 不可用时拒绝创建，不自动 fallback。不同实际目录按既有并发调度，同目录串行；续聊和恢复使用已绑定目录，已有 Local 历史不自动迁移。不自动回写、清理或提供一键回滚。存储、平台限制、Sandbox、记忆与恢复见 [工作区设计](worktrees.md)。
- D168 替代上述 Windows 部分：WinFsp 原生实时 overlay 直接读取来源工作目录，写入私有层，不复制 repo 或 Git 对象库；通过 no-checkout linked worktree 独立 HEAD/index、共享 objects/refs/common config。挂载采用跨账户可见的本机 UNC；Sandbox 授权虚拟根和核验的公共 Git 根，来源工作文件 ACL 不变。正常排空后卸载/恢复，未知状态拒绝重建；缺 Runtime/helper 明确拒绝。POSIX CoW 与显式 Worktree 保持原行为，具体未支持项及实机证据见 [Windows overlay](winfsp-overlay.md)。
- 关闭页面后，只要后端仍运行，任务可以继续；重启后端后，将未完成任务标记为中断，不自动重放命令。
- 历史对话可以继续交流，但每次重新执行任务时读取当前文件，不把历史内容当成最新代码。
- 限制工具输出和上下文长度；每次主任务模型请求及重试前按完整历史计量，接近容量时自动压缩会话内旧上下文，保留用户原文、原始历史与恢复状态。无法安全压缩时明确停止。跨会话项目记忆使用平台数据目录中的 JSONL 快照（D142、D143）：首行项目元数据、后续每行一条完整记忆；已有项目记忆经备份和完整核对后一次性迁移，运行时不再读取 Markdown 或自动迁移。每个任务按文件顺序提供所有有效条目的 ID、逐条版本与标题摘要，不再关键词评分、排序或按目录条数/字符裁剪，正文和来源通过现有 `memory_apply` 的单条 `read` 操作按需读取；该工具继续支持自动添加、更新和归档同项目记忆，不等待人工确认；read/update/archive 各自校验目标条目的 expectedVersion，create 无需版本，无关条目修改不使旧目录中的其他版本失效，维护批次全成或全不写（D144）；不引入 SQLite/FTS 或向量检索。

  项目管理 UI、来源失效验证和手工恢复/清空仍待实现，见 memory-system.md。详见 context-management.md（D023、D027）；服务公开容量和实际 token 用量按 D024 接入，未知能力不猜测，详见 model-tokens.md。

### Windows Sandbox 范围与验证状态

Windows 专用用户 Sandbox 已通过用户实际使用验证：2026-10-03 用户确认持续使用一段时间功能正常，按可用于日常开发记录（D130）。默认关闭，需要显式安装和启用。macOS/Linux 不加载该 Windows 后端；默认宿主模式，显式启用时选择独立的 [MXC 后端](posix-sandbox.md)。此确认不等于逐项完成所有安全/故障矩阵；subagent 入口由后续 D158 单独开放，不以该确认代替专项验收。

- **执行位置**：常驻 Agent Runtime 在专用账户、restricted token 和 Job 中运行。Broker 保留模型密钥、会话存储和审批；Git CLI 使用普通命令路径；只有显式获批的 `run_with_permissions` 命令由 Broker 执行并记为未受 Sandbox 保护，无 Git 专用 IPC 或隐式转发。
- **Git 仓库信任**：用户要求 Sandbox 启动时为工作目录仓库加入 trust folder（D161）。Windows/MXC 启动准备生成实例级 `safe.directory`，只信任当前仓库真实路径，不修改宿主永久配置或信任全部目录。用户随后同意继承宿主对工作目录生效的 user.name/email，认证仍留在宿主，通过既有审批运行联网命令，不复制凭据或签名配置；详见 [开发说明](development.md#git-cli-权限d155)。
- **持久文件身份（D163）**：每个工作区或显式长期可写根独立的 capability SID 保存在应用数据目录，按真实对象身份跨任务、服务和电脑重启复用；长期根 ACE 保留，execution/IPC、临时目录和账户租约仍按实例管理。旧 ACL 不自动修复，完整撤权与升级边界见 [持久根 capability](windows-root-capabilities.md)。
- **文件与并发**：AccessManifest 投影工作区、显式读写根和运行依赖；实例 token 包含 root capability 与 `Everyone` restricting SID。已有 ACL 允许 Everyone 写入的对象可能绕过 root capability，因此不承诺完整写入隔离。多个实例共用账户，读取根会形成并集，存在 peer 干扰风险；不同对话不是 OS 安全边界，也不承诺纯读取 allowlist。
- **审批与网络**：已有权限内的工具免审批；越界命令用 `run_with_permissions` 提交命令和理由，经三级审批后由 Broker 宿主进程执行，不额外限制文件根、网络目标或宿主可用凭据。Git push 同样按命令权限及显式 DAG 依赖处理，不再固定预检 upstream/URL/OID/ref 或独占批次。独立 Capability/Push Runner 及专属 relay/askpass 已按用户要求移除（D162），旧 kind 仅供历史读取；现行 root capability 和 Runtime IPC 保留，专用账户 WFP 不临时放宽。
- **失败处理**：只有 Runtime 启动前且可证明完整回滚时才自动回退宿主，并明确提示任务未受 Sandbox 保护。Broker 宿主命令和 push 是明确获批的执行位置，不是 fallback。已启动命令或 push 结果未知时不重放；Sandbox 实例清理未知时隔离并排空账户 generation。
- **安装维护**：常规 Repair 保留已验证账户的 SID 与原 DPAPI 凭据，清理活动进程/journal 后更新组件；失败保留账户和恢复 state，不自动删除重建。显式 Uninstall/recover 仍删除账户，已有工作区失效 ACL 不自动修复（D154）。
- **验收边界**：日常功能可用性已有用户实际使用确认；原生构建、协议与 harness 或日常使用反馈，都不能代替未明确覆盖的错误 IPC、复杂 ACL、网络、真实 push 和异常恢复专项证据。工作区直接写入，包含 `.git` 和 `.env`，不提供副作用回滚。

完整权限、失败条件与 W0--W6 验收要求以 [Windows Sandbox 架构](windows-integrity-sandbox.md) 为准；安装和操作见 [使用指南](windows-sandbox-guide.md)。

分级诊断日志是同时适用的开发要求（R18）；历史会话与诊断日志分别管理。

## 3. 技术与目录

技术选型依据见 [technical-proposal.md](technical-proposal.md)；当前配置和权限细则见 [development.md](development.md)。

- 采用 Node.js 24 或 26、TypeScript strict 与 packageManager 固定版本的 pnpm。
- 采用单包仓库；第三方库用于通用基础能力，自研 agent 循环、工具协议、上下文策略和授权机制。
- 已确认采用本机浏览器 Web UI + 本机后端；服务默认仅监听回环地址，用户可显式开放受信任局域网。后端负责模型调用、文件访问和命令执行，前端展示状态并收集用户操作；可由设置页开启单一密码门禁（重启生效），但局域网模式不提供多用户账户、权限分级或公网部署。
- API 密钥保留在后端；后端落实权限判断，校验请求来源和会话身份。HTTP 接收操作，SSE 按事件游标恢复订阅；重新连接不触发任务重放。
- 跨平台实现需处理路径、shell、进程生命周期、文件权限和编码差异；版本与浏览器矩阵确定后安排对应验证。
- 模型层保持小型接口，先落地一种 API 协议，再按实际需要扩展；不预先承诺兼容所有提供商。
- 明确最大步骤、命令超时、上下文容量和重试上限，避免无限循环或无限重试。
- 工具授权是应用逻辑，不能冒充操作系统沙箱。Windows 专用用户/Broker 已实现并通过用户实际使用验证；其 OS 级限制仍以专用账户、restricted token、ACL/Job/WFP 的实际边界为准，只提供有限保密性，不承诺完整读写 allowlist、任务间隔离或跨平台 Sandbox。后续安全能力声明须有对应专项证据。

模块结构方向（实际目录和职责见 architecture.md）：

```text
src/
  web/          # Web UI、交互、状态展示
  server/       # API、事件传输、会话接入
  agent/        # 循环、停止条件、任务状态
  providers/    # 模型协议适配
  tools/        # 工具定义与实现
  permissions/  # 权限规则与确认流程
  context/      # 上下文构建与预算
  sessions/     # 历史持久化、读取与续聊；中断状态管理
  config/       # 配置加载与校验
tests/          # 按行为组织验证
docs/           # 需求、架构、开发说明和决策
AGENTS.md
README.md
```

依赖方向：Web UI 通过 API 与 server 交互，server 调用 agent，agent 依赖工具和模型接口；核心机制不依赖 Web UI。前端不得直接导入文件访问、命令执行或密钥配置模块。共享类型靠近所属模块，避免无边界的 utils 目录。

## 4. Git 工作流与产品 Git 操作

区分两个问题：

- **开发本项目**：建议按文档基线、基础骨架、最小闭环、工具能力等独立可验证增量提交；每个增量同步更新文档。commit 使用英文；分支和 PR 策略仍按项目约定处理。
- **产品操作用户仓库**：用户确认移除专用 `git` 工具，改用 Git CLI（D155）。宿主 `run_command` 沿用命令审批；Sandbox Runtime 已有权限内直接执行，需宿主网络、凭据或文件权限时显式提交 `run_with_permissions`，Broker 重新审批完整命令和理由。

不引入 Git 关键词识别或自动转发，不保留旧 action、工作区根、敏感模板、revision、upstream/OID/ref、hook/签名禁用和 push 独占约束；Git 配置及子进程按实际执行身份运行。模型应先检查状态/差异/历史、仅暂存预期文件、推送前核对目标、同仓库写操作声明依赖；这些是工作流指导，不是 Git 专用硬边界。取消或结果未知不自动重放。旧 Git 记录继续可读，新请求拒绝执行，无需历史库迁移。

## 5. 初版验收标准

- 在测试项目提出“修复一个 bug 并补充测试”：agent 读取项目约定与相关代码、修改文件、运行测试、展示 diff 与结果；需要授权时暂停等待；重启后仍能查看此次对话及工具记录。
- 对循环与工具错误使用可重复的模拟模型测试；真实 API 验证作为单独步骤，不要求所有测试持有密钥。
- 工具失败、模型失败、命令超时和用户取消时能够停止或有界恢复，并报告真实状态及实际错误信息；错误信息在保存、展示和日志记录前必须脱敏、限长。
- 未授权操作被拒绝；路径越界、链接路径和命令执行的边界有明确说明和相应验证。
- 新使用者根据 README 可完成配置并运行示例；敏感配置不会进入版本控制或默认日志。
- 修改模型协议或增加工具时，不需要重写 Web UI 与 agent 主循环。
- 在 Windows、macOS 和 Linux 的约定环境中分别验证安装、启动和编码任务闭环，记录实际验证平台与未覆盖项。
- 在 Web UI 完成任务输入、进度查看、权限确认、diff 查看和取消；刷新或断线时能准确展示任务状态，后端仍运行时任务继续，后端重启后标记中断且不重放命令。
- 验证默认配置下 Web UI 和后端服务仅绑定回环地址；设置 `CODEATELIER_LISTEN_ADDRESS=0.0.0.0` 或 `::` 后可从受信任局域网访问，仍不作为公网服务部署；已配置的模型 API 调用正常工作。

- 日志验收：默认 INFO 时不输出 DEBUG/TRACE；日志文件和终端使用紧凑的格式化纯文本而非 JSON，开启调试后能够通过关联标识追踪一次任务的模型调用、工具执行和失败原因；失败记录包含脱敏、限长的错误消息、受控元数据、原因链和堆栈，不能只留错误类型。各级别日志均不泄露密钥等凭据，长字段受限。实现采用 Pino、平台数据目录和 5 份轮转日志，详见 development.md。

## 可选辅助模型（2026-09-12）

用户要求增加低成本模型配置，供会话标题、工具使用审批、上下文压缩等辅助任务使用。当前实现提供独立模型 ID 和思考等级配置，并接入摘要及首条用户 prompt 的自动标题：新会话先显示“新对话”，标题请求使用辅助模型并在成功后更新历史与 UI；失败保留占位标题且不阻断编码任务，取消会中止任务。空配置下标题与摘要沿用主模型；标题请求没有工具，遇到可重试或无可分类原因的模型调用错误时在首次失败后最多自动重试 3 次。

每个原本需要审批的命令或工具使用都会向已配置的低成本辅助模型发送后端从会话读取的工作区根目录、工具名和待审批内容，无工具、单次将 `reasoning.effort` 设为 `none` 的 256 token 分类请求（不改变辅助模型设置），结果为 `approve`、`human review` 或 `reject`：前者自动通过，第二项保持当前人工点击流程，第三项直接拒绝并展示理由。

模型以会话工作区根目录解析命令和组合的实际影响，优先 `approve` 没有明显负面或恶性影响的请求：工作区内普通读写与常用开发命令、无害的管道/组合，以及合理的公开网络读取、公开依赖获取或工作区外非敏感只读访问。cwd 不是访问边界，不能仅凭命令名推断安全；但路径越界或网络访问本身也不是转人工理由。工作区外写入、敏感内容、重大破坏或系统影响等具体风险转人工；明确恶意窃密、破坏或绕过边界才直接拒绝。对普通程序的抽象不确定性不单独触发人工确认；宿主 Broker 命令按完整宿主权限评估。缺少辅助模型、模型故障或无效输出均保守降级为人工确认，不使用主模型代替低成本审批；任何分类都不放宽执行器的既有安全校验。
