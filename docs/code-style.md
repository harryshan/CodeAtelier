# 代码可读性与审核约定

这是长期开发要求：代码首先应让维护者看懂职责、执行顺序、错误处理和副作用。适用于手写源码、测试、脚本和配置；不手工重排依赖、锁文件或构建产物。

## 分段与命名

- 导入与实现、独立函数和类方法之间留空行。紧密相关的字段、参数或断言可以保持在同一段。
- 一段承担一个逻辑步骤，例如校验输入、读取状态、执行操作、保存结果和清理资源。不要每行都插空行，也不要用大片连续代码隐藏步骤边界。
- 条件和循环始终使用花括号，一次声明一个变量，避免多个副作用挤在同一行。
- 名称说明用途。短循环索引可以用 i；任务环境、刷新状态、持久化结果等应使用可辨认的名称。
- 长函数中可独立解释的职责提取到具名函数或模块，保持调用顺序清晰；不为了缩短代码而过度拆分。
- SQL、提示词和测试数据也要便于阅读；重排时注意字符串内容、字段顺序和协议语义。

## 文件与模块职责

- 文件名反映主要类或职责，重要类拥有容易直接定位的文件，例如 ToolRunner 位于 tools/tool-runner.ts。
- 参数契约与执行副作用分开；通用接口不依赖具体提供商。纯脱敏、路径等函数不应因为复用而加载日志或工具执行实现。
- HTTP 来源校验、SSE 生命周期、浏览器连接管理等独立职责分别组织，入口保留组装与调用顺序。
- 不要求每个微小类型单独成文件；共享数据契约和同一职责的辅助函数可以集中。避免只转发导出的兼容空壳掩盖真实归属。
- 移动模块须更新源码、测试、脚本及文档中的引用，并运行原有行为回归。

## 文件级说明（永久标准）

- 每个手写代码文件必须在文件开头说明“文件作用”和“代码结构”：前者解释它在 CodeAtelier 中承担什么职责，后者按实际顺序概述主要入口、类型、类、函数或执行阶段。
- 覆盖生产源码、测试、测试夹具、开发脚本、样式、HTML 和支持注释的工具及 CI 配置。测试文件说明覆盖主题及用例组织，脚本说明入口与阶段；评测脚本注明手动执行边界。
- TypeScript、JavaScript 和 CSS 使用块注释；Python、Shell、PowerShell 和 YAML 使用行注释；HTML 使用 HTML 注释。保留 shebang、编码声明和 doctype 的必要位置；保留现有模块文档字符串和许可证说明。
- JSON 等不支持注释的配置不得插入非法注释，其用途和结构在相关开发文档中维护。依赖、锁文件、构建产物和自动生成文件不手工添加文件头；生成模板由维护者按需维护。
- 文件头必须提供足够具体的阅读导引，不能停留在“负责某模块，先初始化再执行”这类两句概述。说明谁调用它、与哪些模块协作、接收和产出什么，以及状态保存、权限、取消、失败或其他副作用的关键边界。
- “代码结构”必须分项，按源码的实际组织顺序说明主要类型、类、方法、辅助函数或执行阶段，并使用可定位的符号名。核心流程须交代数据如何流转，例如模型响应何时保存、工具何时执行、结果何时落盘；不只罗列名称。
- 测试文件说明夹具和模拟边界、用例分组及关键可观察断言；脚本说明调用入口、准备/执行/输出/清理阶段及真实服务或文件副作用；类型与配置文件说明使用者、字段分组和关联维护位置。
- 细节与文件复杂度匹配：小入口或纯类型文件仍需写清调用关系与实际组织，但不虚构不存在的阶段；大文件应按职责分组形成阅读路径。避免复制空泛模板、逐行翻译、罗列全部符号或写死易过期行号。
- 建议采用“文件作用 → 模块协作或使用场景与输入输出 → 分项代码结构 → 关键约束或维护注意事项”。栏目名称可按文件类型调整，内容准确、可定位且足以理解实现才是验收标准。
- 新建文件时同步编写；修改文件职责、主要入口、模块分组或执行顺序时，在同一变更中更新说明。即使已有文件头，也必须在编辑和提交审核时核对，不能把首次补齐当作一次性任务。

## 注释

注释解释“为何如此”和“必须保持什么”，重点覆盖：

- 已知工具结果为何可以补齐，而未知副作用不能自动重放。
- 审批后为何还要重新核对路径与文件内容。
- 日志、任务状态与数据库事务的失败边界。
- 自建模型服务的兼容处理，以及浏览器重连、服务退出的时序。

不要为简单赋值写逐行翻译，不要留下过期注释或仅适用于某次修改的过程记录。公共边界按需说明输入约束、副作用和返回结果，不要求每个函数都写形式化注释。

## 测试与审核

测试用例之间分段；准备、执行、断言和清理应容易辨认。名称描述用户可观察行为，断言验证实际结果。可读性重构沿用相关回归测试；如果顺带改变行为，必须增加相应测试和需求说明。

提交前检查：新增和修改文件的文件级说明是否齐全、是否与当前职责和结构一致，是否能据此定位主要入口、看懂模块之间的数据流和重要失败边界；读者能否快速定位功能入口、理解主要步骤、看清哪些操作会修改状态，以及失败后会发生什么。

## 工具

- `pnpm format`：格式化源码、测试、脚本和根目录工具配置。
- `pnpm format:check`：只检查格式，已经纳入 `pnpm check` 与 CI。
- ESLint 校验花括号、变量声明和基础段落间距。

工具保证一致排版；段落是否合理、注释是否必要、命名是否清楚仍由开发者审核。
