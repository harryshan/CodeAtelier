# 代码可读性与审核约定

这是长期开发要求：代码首先应让维护者看懂职责、执行顺序、错误处理和副作用。适用于手写源码、测试、脚本和配置；不手工重排依赖、锁文件或构建产物。

## 分段与命名

- 导入与实现、独立函数和类方法之间留空行。紧密相关的字段、参数或断言可以保持在同一段。
- 一段承担一个逻辑步骤，例如校验输入、读取状态、执行操作、保存结果和清理资源。不要每行都插空行，也不要用大片连续代码隐藏步骤边界。
- 条件和循环始终使用花括号，一次声明一个变量，避免多个副作用挤在同一行。
- 名称说明用途。短循环索引可以用 i；任务环境、刷新状态、持久化结果等应使用可辨认的名称。
- 长函数中可独立解释的职责提取到具名函数或模块，保持调用顺序清晰；不为了缩短代码而过度拆分。
- SQL、提示词和测试数据也要便于阅读；重排时注意字符串内容、字段顺序和协议语义。

## 文件与模块职责

- 文件名反映主要类或职责，重要类拥有容易直接定位的文件，例如 ToolRunner 位于 tools/tool-runner.ts。
- 参数契约与执行副作用分开；通用接口不依赖具体提供商。纯脱敏、路径等函数不应因为复用而加载日志或工具执行实现。
- HTTP 来源校验、SSE 生命周期、浏览器连接管理等独立职责分别组织，入口保留组装与调用顺序。
- 不要求每个微小类型单独成文件；共享数据契约和同一职责的辅助函数可以集中。避免只转发导出的兼容空壳掩盖真实归属。
- 移动模块须更新源码、测试、脚本及文档中的引用，并运行原有行为回归。

## 注释

注释解释“为何如此”和“必须保持什么”，重点覆盖：

- 已知工具结果为何可以补齐，而未知副作用不能自动重放。
- 审批后为何还要重新核对路径与文件内容。
- 日志、任务状态与数据库事务的失败边界。
- 自建模型服务的兼容处理，以及浏览器重连、服务退出的时序。

不要为简单赋值写逐行翻译，不要留下过期注释或仅适用于某次修改的过程记录。公共边界按需说明输入约束、副作用和返回结果，不要求每个函数都写形式化注释。

## 测试与审核

测试用例之间分段；准备、执行、断言和清理应容易辨认。名称描述用户可观察行为，断言验证实际结果。可读性重构沿用相关回归测试；如果顺带改变行为，必须增加相应测试和需求说明。

提交前检查：读者能否快速定位功能入口、理解主要步骤、看清哪些操作会修改状态，以及失败后会发生什么。

## 工具

- `pnpm format`：格式化源码、测试、脚本和根目录工具配置。
- `pnpm format:check`：只检查格式，已经纳入 `pnpm check` 与 CI。
- ESLint 校验花括号、变量声明和基础段落间距。

工具保证一致排版；段落是否合理、注释是否必要、命名是否清楚仍由开发者审核。
