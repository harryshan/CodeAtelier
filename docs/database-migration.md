# SQLite 存储改造与完整历史迁移

状态：交接设计，尚未实现或执行。记录日期：2026-10-11；审查修订：2026-10-12。用户决定及本次文档补充见 D148，位于 [决策记录](decisions.md)。

本文供后续外部开发工具实施。用户明确不采用 PostgreSQL，并要求旧对话记录也完整迁移；本次任务只记录文档，不修改存储实现、不操作真实历史库、不自动关闭或重启服务。线程数量、目标表结构、schema 版本、命令名称和性能阈值仍需在实现阶段确定，本文不提供尚不存在的迁移命令。

## 1. 已确认要求与交接边界

- 保留 SQLite 和本机部署，不增加数据库服务。
- 所有源历史分片中的旧对话及关联记录都必须完整迁移到选定的目标存储版本，完成全量验证后才能切换。
- 不能仅迁移新任务、最近会话或页面可见消息；不能把旧正文留在旧库并以兼容读取、首次打开时转换或后台慢慢补齐冒充迁移完成。
- 源格式适配器可以用于离线迁移、校验及测试，但正式切换后，历史浏览、续聊和 Replay 不应再依赖原始数据库。
- 缺失的历史事实继续缺失：旧任务没有捕获的模型请求不能生成假请求；未知、未完成、legacy、截断等状态必须保留。
- 迁移还须覆盖顺序、序列化兼容和压缩消费者的行为验证，并制定空间治理与验收要求。区分物理碎片、正文重复、正常历史增长和 WAL 占用；不以换 Worker 或新库重建宣称永久消除碎片。
- 用户会使用其他工具实施，避免使用正在保存本次工作的 CodeAtelier 同时改造其自身数据库。开发可使用合成夹具和独立副本；正式源快照必须在本对话保存完成、服务与全部写入者停止后重新取得。
- 本文不是关闭服务、读取外部数据目录或迁移真实数据的工具授权；执行方仍须遵守自己的权限与操作确认规则。

本要求替代此前讨论中“旧格式长期保留兼容读取、不强制改写旧历史”的迁移建议。实现可以分阶段开发，但上线交付必须通过全部旧记录转换与核对门槛。

## 2. 当前代码基线与风险

以下为仓库代码基线，不是对用户实际数据库内容、大小、损坏或性能的诊断；实施前需重新读取当前代码与源 schema。

- [schema.ts](../src/sessions/schema.ts)：当前 `user_version=10`，主体正文保存在 TEXT JSON 中。
- [store.ts](../src/sessions/store.ts)：历史、上下文和快照先经主线程 `serializedSize` 查询，再按阈值选择同步读取或 Worker；仍保留同步写入和遍历分片开启事务的入口。
- [store-worker.ts](../src/sessions/store-worker.ts) 与 [store-worker-queue.ts](../src/sessions/store-worker-queue.ts)：读写共用串行队列，线程复用但每次请求重新打开、关闭连接。
- [history-shards.ts](../src/sessions/history-shards.ts)：约 1 GiB 后让新会话进入后续分片；一个会话始终留在原分片，任务和会话定位逐分片查询。
- [replay-storage.ts](../src/sessions/replay-storage.ts)：兼容旧整条捕获与 `storageVersion=2` 增量捕获；新模型请求通过 `lastInput` 从此前全部模型记录重建上一输入。
- [engine.ts](../src/agent/engine.ts) 的 `snapshot` 和 [replay-routes.ts](../src/server/replay-routes.ts)：初始会话读取全部事件，Replay 页面同步完整重建单任务。
- [context.ts](../src/agent/context.ts)：续聊读取全部事件寻找缺失工具结果；[session-statistics.ts](../src/web/session-statistics.ts) 及 [session-view.ts](../src/web/session-view.ts) 的统计依赖事件历史。
- [context-manager.ts](../src/context/context-manager.ts)：正常压缩与兜底压缩也读取全部会话事件，并交给压缩 Worker 还原工具材料、构建执行账本；不能只改浏览和恢复查询。
- `Store.tasks`、`latestContextSnapshot` 和 `subagents` 分别依赖隐式 `rowid` 保持同时间任务顺序、选择最新快照和排列子任务。仅保留实体 ID、正文及父链不足以保持这些读取行为。
- [token-anchor.ts](../src/context/token-anchor.ts) 对协议项的序列化文本计算指纹；[tool-result.ts](../src/context/tool-result.ts) 将事件结果的 `JSON.stringify` 与上下文 output 字符串精确比较。JSON 值等价不代表这些消费者兼容。

特别注意：不能以 `new Store(source, { interruptActive: false })` 充当只读源检查器。该选项仅控制启动中断标记，构造路径仍会初始化 schema、迁移以及可能生成升级备份。源盘点和迁移读取器必须独立设计为只读，不执行现有 Store 构造器副作用。

## 3. 目标运行期架构

### 3.1 单写入口、独立读取、连接复用

建议保留现有 Node 内置 SQLite 接口，不把驱动更换或 ORM 引入混入本次改造。由异步 Store 接口连接一个写 Worker 与少量有界读 Worker，初始评估配置为一个写 Worker、两个读 Worker，不按会话或分片无限创建线程。这些是实现建议，不把线程数量等细节冒充用户逐项确认。

- 所有运行期写入收敛到写 Worker：会话、任务、标题、事件、上下文、token 锚点、Replay、压缩及现存 subagent 账本；不因此开放 subagent。
- 暴露固定业务操作，例如创建任务并记录用户输入、保存工具结果、提交压缩，不传递任意 SQL 或任意事务回调。
- Worker 按需打开分片连接，连接与 prepared statement 有界复用；事务结束后才允许回收连接。
- 每笔事务只涉及所属分片，不再为单会话操作锁定所有分片，不承诺跨分片原子性。
- 序列化、比较等准备尽量移到持锁阶段之外；只有提交成功才更新缓存、返回成功、发布对应 SSE 通知。
- 有因果依赖的读取等待对应提交回执；一致视图通过同一读事务取得。长浏览或导出不得无限持有读事务。
- 初期保持单写入口与已有全局事件游标语义，明确 ID 分配、提交和通知顺序，不把多个写队列与新排序机制一并引入。
- 关闭时拒绝新业务、排空已接受的写入、处理读请求取消，然后关闭连接和线程。读取消不得中断正在提交的写 Worker。
- 队列同时限制请求数量和数据预算；背压或拒绝必须有明确结果，不静默丢弃关键历史。写 Worker 崩溃时区分尚未发送与已发送未确认请求，不盲目重放未知提交。

工具结果的事件、Replay 和上下文反馈保持同一分片事务。宿主与 Sandbox Runtime 的调用方都要核查；当前分开的 IPC 请求不能仅靠换 Worker 就宣称获得跨请求原子性。

### 3.2 查询与分片定位

- 删除主线程 `serializedSize` 预检，历史、上下文和快照统一异步读取，不以更换长度函数作为最终修复。
- 需要大小信息时，在序列化后保存真实字节数，供分页和诊断使用，不在每次读取前重新汇总全文。
- 为任务事件、会话任务排序、未完成任务和恢复关联查询增加匹配索引，以实际查询计划验收；不要为所有字段盲目加索引。
- 将所有具有业务含义的隐式 `rowid` 顺序转换为显式稳定顺序：任务保留 `createdAt` 相同情况下的顺序，快照保留每会话的插入顺序和最新快照选择，子任务保留每主任务的计划顺序。迁移读取原始顺序并确定映射，新写入沿同一规则分配；不得改用随机 ID、时间戳猜测或目标插入顺序代替。
- 增加可重建的会话、任务到分片的轻量缓存，提交后更新，不建立需要跨文件原子维护的第二份权威目录库。
- 保留约 1 GiB 的新会话分片策略以及会话不跨片的事务边界；本次不自动重新分区超长旧会话，也不承诺分片硬性不超过阈值。

### 3.3 四类读取接口

页面浏览、任务恢复、模型上下文和 Replay 必须分开设计，不能给当前所有查询统一加 `LIMIT`。

1. 页面首屏只取会话信息、活动状态、审批、完整统计与最近任务摘要。历史按任务展开、事件分页、正文按需分段；分页兼顾记录数与字节数，不能静默截断存储内容。
2. 历史翻页与实时增量使用不同游标。固定追加事件读取上界，明确 `hasMore` 与续读规则；处理工具开始、输出、结束跨页关联，前端详情缓存有界。
3. 统计使用带规则版本、处理水位且可重建的投影，运行期与事件同事务更新。正式迁移中为所有旧会话完成回填，不能切换后才慢慢补齐。缺失 usage 与旧请求计数的兼容语义不变。
4. 恢复先读完整活动上下文，再针对缺结果的调用查询结果和执行实例；需要可索引的关联字段或派生关联表。源数据缺失不能解释为工具未执行，继续保留未知结果禁止重放。
5. 活动上下文继续按批次增量保存；压缩快照、新基线、token 锚点处理保持原子关系。大输入允许分批运输，但消费者最终需要完整输入的内存成本仍须明确。
6. 正常压缩与兜底压缩使用专门的完整材料查询：按本次处理的协议项、祖先快照和工具调用读取所需结果，避免每次加载全部事件。关联索引必须保留任务归属、同名调用 ID 的多个候选及精确结果匹配语义，不能按 call ID 覆盖为一条，也不能只查询缺结果的调用。查询固定读取水位，跨批次完整收集候选后再判断唯一匹配；保留原文还原、错误、截断和 unknown 语义，不复用 UI 的最近页或静默 `LIMIT`。
7. Replay 页面先取请求目录，再读取选中请求及关联工具。完整 `TaskReplayCase` 保留为导出协议，而非默认页面响应。查询仍校验会话归属与现有访问门禁。

恢复与压缩查询涉及 `TaskContextStore`、`ContextManager`、压缩 Worker、Runtime session client、Broker handler 及 IPC schema；接口变化须同步版本、bundle 和安装更新说明，不能只改宿主路径。新查询须在相同输入下对照原全量路径验证；分批读取仍须声明单条超大材料、完整模型输入和快照链的内存成本。

### 3.4 Replay 与正文组织

- 短期可在写 Worker 中缓存活动任务最近已提交输入；缓存有预算，任务结束释放，回滚不推进，失效后可从持久记录恢复。
- 目标 Replay 编码应支持检查点与增量，按链长和累计字节量限制重建距离；请求材料与响应终态分离，减少终态更新时的整条读出、合并和序列化。
- 完整迁移必须将旧整条 JSON 和已有增量格式转换到本次确定的目标编码，不能只给新任务加检查点。没有捕获材料的 legacy 任务保留真实的 legacy 来源状态，同时完成其已有材料和索引的迁移。
- 必须处理不同请求用途、压缩后输入变化、重试及没有终态的请求，不能假定下一输入总是前一输入的追加。
- 同分片不可变正文去重与压缩作为可选后续优化，不是第一阶段前置条件。若本次采用，则所有适用旧载荷也须转换及校验，不以旧库引用作为去重捷径。
- 去重只复用完全相同且采用一致脱敏策略的材料，先限于同会话或任务；UI 结果、截断反馈与完整 Replay 不混同。正文及引用在同一 SQLite 事务提交，不引入外部文件双写。

目标 DDL、格式编号与检查点参数必须在正式迁移前冻结，不能仅修改 `user_version` 或把旧 JSON 封存到无人读取的列就声称完成目标改造。

### 3.5 序列化兼容

- 逐字段定义比较契约。原始文本、嵌入 JSON 的字符串、活动上下文及快照协议项、用于精确匹配的事件工具结果，须保留现有消费者所依赖的序列化表示，包括对象键顺序。仅在证明没有指纹、文本匹配或其他序列化依赖时，才允许采用对象键无序的语义比较；不能对所有 JSON 统一排序、格式化或重新脱敏。
- 校验活动输入在锚点 `inputItems` 范围内的 `tokenPrefixHash`，并核对相同 scope、instructions、tools 下锚点恢复结果与迁移前相同。原本因模型配置或工具定义变化而不适用的锚点可以继续不适用，但必须保留原记录并报告原因，不能伪造新的校准值；迁移造成的新指纹差异阻止切换。
- 对事件工具结果与上下文 output 使用生产匹配规则交叉核对，确认迁移前后结果关联、原文还原和执行账本一致。既不能把 recorded 降为 unknown，也不能因去重或丢掉歧义候选把 unknown 升为 recorded。

### 3.6 物理碎片、空间增长与 WAL 治理

本节是待实施的治理要求。独立新库导入可改善旧布局，但运行期仍可能产生空闲页和页内空洞；异步 Store、连接复用和单写 Worker 不负责整理物理碎片。保留历史分片是容量策略，不把多个 SQLite 文件视为碎片故障，也不因此合并或重新分区旧会话。

- **分开测量**：逐分片记录主库字节数、`page_size`、`page_count`、`freelist_count`，用空闲页数乘页大小估算可复用空闲空间，空闲页比例仅表示整页空闲。另统计表/索引的页内利用率及布局分散情况；可使用 SQLite `dbstat`，但须确认实际运行时支持，并说明统计口径。不可用时记录限制并用支持该能力的只读副本分析工具补测，不能把未知报告为零碎片。
- **区分增长来源**：分别记录逻辑正文量、重复材料、索引/检查点开销、空闲空间、WAL 当前及峰值大小。正文去重/压缩仍按第 3.4 节单独评估；VACUUM 不去重业务内容，Replay 检查点也可能用空间换读取速度。活跃 generation、旧 generation、备份和临时文件分开计量，保留备份期间不承诺整个数据目录变小。
- **运行期 WAL**：由写入口统一明确并验证每个写连接的自动 checkpoint 阈值及维护职责；默认 SQLite 自动 checkpoint 不能被误称为不存在，也不能代替应用验收。优先评估不会等待读者结束的 PASSIVE 策略，记录完成帧、剩余帧、耗时及错误；未完成须保留原因并有界处理。长读事务设置寿命和取消释放规则，不能无限阻碍 checkpoint，也不能用取消读请求中断业务提交。
- **离线整理**：提供显式维护流程，在停止业务、排空写入、释放读事务且备份有效后按分片评估 VACUUM；只有完成显式顺序改造和空间预检后才能执行。迁移目标的整理放在最终验证之前。TRUNCATE checkpoint 仅在受控维护窗口评估使用，不在每次提交后强制执行；禁止直接删除 WAL，checkpoint 也不等于整理主库。
- **配置与失败**：在目标冻结前明确 `auto_vacuum`、checkpoint、忙等待和持久性配置，以及跨连接的设置方式。不开启 `auto_vacuum=FULL` 来冒充碎片整理；它只回收整页空间，不能压实页内空洞，且可能增加碎片。不得为缩小体积或跑分静默降低提交持久性；维护失败保留原库和备份，记录状态后停止该维护流程，不自动重放业务。
- **验收门槛**：先用固定合成历史和固定追加/更新/上下文压缩负载建立基线，再冻结空闲页、页内利用率、单位逻辑数据的物理增长、WAL 峰值/回落时间和维护耗时的阈值。正式迁移前必须补齐数值、负载、采样方法及不适用项的理由；完整迁移不能仅以“文件变小”或“新库已创建”验收。页布局变化还需结合读写延迟评估，不承诺零碎片或历史持续增长时文件不再增大。

SQLite 行为依据：[VACUUM 与隐式 ROWID](https://www.sqlite.org/lang_vacuum.html)、[备份 API](https://www.sqlite.org/backup.html)、[WAL 与 checkpoint](https://www.sqlite.org/wal.html)、[PRAGMA 配置](https://www.sqlite.org/pragma.html)、[DBSTAT 页统计](https://www.sqlite.org/dbstat.html)。实施时核对所用 Node 内嵌 SQLite 的版本与编译能力；这些机制说明不是现有产品维护命令。

## 4. 完整迁移的数据清单

迁移单位是全部源分片中的全部会话及关联记录，不是单个 UI 页面或某种任务终态。以下是基于当前 schema 的最低清单，实施时还要检查实际表、列、索引和版本差异。

- `sessions`：ID、标题、工作区、创建和更新时间、标题生成状态；不重新生成标题或改写工作区路径。
- `tasks`：ID、所属会话、状态、创建/开始/结束时间、错误、subagent 标记及稳定排序；失败、取消、中断、未完成任务同样迁移。
- `events`：所有事件类型、ID、会话和任务关联、时间、完整 data，包括用户消息、回复、命令输出、参数、结果、审批、执行实例、usage、恢复信息及未知事件类型。
- `context` 与 `context_chunks`：旧基线和增量按源版本规则重建，保留全部协议项及顺序、call ID、缺结果事实。两者同时存在且关系无法解释时停止，不能重复拼接或随意丢弃其一。
- `context_token_anchors`：保留校准锚点及关联，按第 3.5 节验证序列化指纹与恢复行为；区分既有不适用状态和迁移造成的不兼容，不静默丢弃校准基线。
- `context_snapshots`：全部快照 ID、source、摘要、关联、父链和显式顺序；逐会话保留最新快照选择。已发布的历史引用仍能通过原 ID 回读，不能只迁移最新摘要。
- `task_replays` 与 `replay_entries`：元数据、逐次模型 input/instructions/工具定义/选项、响应或错误、工具参数与结果、捕获顺序、未完成状态；增量必须实际解码后核对。
- `subagents` 与 `subagent_requests`：计划及其顺序、检查点、上下文、报告、消费状态、请求 ID、种类、回执及 unknown 状态，不能因功能尚未开放就丢弃已有数据。
- 序列与顺序：保留对外可见的事件、快照、任务和调用 ID；核对最大事件游标、分片局部序列和续写分配，内部键变化须有确定映射，不破坏外部引用。
- 新建派生数据：所有旧会话的统计、调用关联、正文长度和目标 Replay 检查点均需完成构建并验证，不能留未迁移队列。

所有未知扩展字段都要保留或提供明确的无损映射。遇到未知表、源版本、坏 JSON、违反所属作用域唯一约束的重复 ID、断链、孤立引用或无法转换的记录，列出受限诊断并停止切换；不得跳过坏记录后显示成功，也不得自行修复历史事实。调用 ID 不保证跨任务全局唯一，合法重复及原有匹配歧义必须保留，不能去重后当作修复完成。

SQLite 外的 `traces`、项目记忆、设置、配置、日志及既有备份不转存到 SQLite，也不得随切换删除或覆盖。盘点并保留必要的文件及 ID 引用；诊断日志与凭据不进入迁移报告。迁移不访问或改动会话关联的用户工作区。

## 5. 正式迁移流程：停写、复制转换、全量核对、切换

### 5.1 开发与演练

先使用合成库或独立备份副本开发转换器、验证器和新运行时。不要把正在提供本对话的数据库当开发夹具。演练报告不能替代最终停写快照的全量验收。

执行方在文档中补齐：实现提交、源支持版本矩阵、目标 schema/Replay 版本、显式顺序和序列化契约、实际可执行命令、数据目录发现方式、磁盘空间需求、空间治理配置与验收阈值、平台及运行时版本。未补齐前不运行正式迁移。

### 5.2 停止全部写入者

1. 保存本轮对话，等待任务完成或通过正常关闭流程保存为中断；记录无法确认的执行状态，不重放工具。
2. 关闭 CodeAtelier 后端及自动重载/拉起路径，排空 Store 写入，关闭 Runtime/Broker 会话持久化通道和数据库连接。
3. 核对其他进程、旧安装副本和外部工具未在写入同一数据目录。不能把浏览器关闭、暂时拿到数据库锁或一个不被其他工具遵守的标记文件当作充分停写证明。
4. 设置迁移期间的启动拒绝机制与唯一操作者约束，明确只在完成或人工核对后解除。具体机制需实现和验证，本版本尚不存在该迁移门禁。

无法证明停写、任务仍在执行或清理状态未知时停止，不进入正式转换。本次文档任务不代替用户执行上述操作。

### 5.3 冻结源与备份

- 盘点 `history.sqlite`、全部编号分片以及各自关联的 WAL/SHM 状态，不能只复制最新分片或主文件。
- 生成具有 SQLite 一致性保证的备份，并保存源清单、版本、大小、摘要和所需恢复材料；不能直接复制仍在写入的主文件并声称备份完整。
- 冻结输入必须保留隐式 `rowid` 的业务顺序证据。优先使用保留页内容的 SQLite backup API，并核对原始读取顺序与备份一致；若采用 VACUUM INTO 等重建方式，必须在重建前从同一停写输入单独导出带实体归属的顺序映射并绑定清单摘要。不能从已重建副本猜回原始顺序，也不能仅因为备份事务一致就认定隐式 `rowid` 保持不变。
- 如果上次关闭不干净，保留原始文件集，在独立工作副本上通过 SQLite 正常恢复和生成一致性快照，不删除 WAL 强行启动，不在原件上试验修复。
- 对冻结的一致性快照进行结构及引用检查。源缺陷必须报告并停止或另行处理，不能借迁移静默修改。
- 备份和转换目标处于受保护的本地数据目录，权限不得比源宽；不上传、不提交仓库，不把正文写进普通日志。
- 估算备份、目标、索引、WAL 和临时空间，磁盘不足提前拒绝，不能靠删除唯一备份继续执行。

清单记录源分片集合及每片快照摘要，正式恢复迁移必须匹配同一冻结输入。工作副本、原件、备份和目标不得为同一路径或同一文件别名。

### 5.4 独立目标库转换

- 创建独立目标 generation/目录，默认保留源分片与会话归属；不原地改源，不混用新旧分片。
- 按源版本使用显式适配器，只读输入；先导入基础关系，再按确定顺序转换事件、上下文、快照、Replay 和子任务账本，构建派生索引与统计。
- 分批、限内存处理，允许旧任务本身很大；不把全部历史拼成一个进程内 JSON。
- 每批目标数据与该批已提交进度在同一目标分片事务保存。进度记录源摘要、适配器/目标版本和稳定游标；跨分片总体状态从逐片已提交结果核对，不假装跨文件原子提交。
- 中断后先核对源、目标及已提交进度，再明确续跑；已提交内容不得重复插入，部分失败不得覆盖原件。恢复的是数据转换，不是历史 agent 或工具执行。
- 不支持的输入或转换异常保留源、备份和受限故障报告，禁止将未完成目标用于服务启动。
- 全部导入及索引构建结束后，记录目标空间指标，按冻结阈值判断是否需要离线整理；记录执行结果或不需要整理的依据。确认顺序读取已使用显式列后，才可在独立目标上执行所需 checkpoint/VACUUM。整理中断须重新核对目标与已提交进度，不能沿用此前 verified 状态。
- 整理完成后再执行第 5.5 节的最终全量验证并生成最终目标清单；任何后续逻辑或文件重建变更都使旧验证标记失效。不整理、不删除源与唯一备份来腾空间。

### 5.5 全量验证

以下检查全部通过才允许标记目标为 verified；随机抽样和“数量差不多”不构成完整迁移验收。

1. **结构检查**：逐分片完整性、外键、唯一约束及业务引用检查；不能仅依赖当前 schema 中已有的外键，因为并非所有关联都声明了外键。
2. **覆盖检查**：比较全部源会话/任务/事件/快照/调用 ID 集合及归属，按实体和会话记录数量、缺失、重复和意外新增。物理表拆分后按逻辑记录映射核对，不要求所有物理行数相等。
3. **正文检查**：对所有逻辑记录按第 3.5 节的逐字段契约编码和摘要核对。字符串、源码、换行、空白和数组顺序不规范化；只有确认无序列化依赖的对象才能按键无序比较。null、缺字段、空串、数字及重复关联必须区分；不可逆的原始载荷应原样保留而非被解析器吞掉。
4. **上下文与快照检查**：逐会话重建活动输入，核对协议项、锚点前缀指纹及恢复行为、所有快照 source 和父链，以及历史工具引用按原 ID 可访问。对照实际结果匹配规则验证原文还原和执行账本，不能仅比较 JSON 语义。
5. **Replay 检查**：逐任务逐请求比较完整重建输入、instructions、选项、工具定义、响应/错误、工具材料及顺序；覆盖旧整条与增量格式，保留 legacy 和未完成标志。不能只对比增量尾部或最终一次请求。
6. **状态与派生检查**：任务状态/时间、未知执行、报告消费状态、统计和恢复关联完整一致；逐会话对比有序任务 ID 列表、快照顺序和最新快照 ID，逐任务对比子任务顺序。新事件 ID 分配不冲突、不倒退，不伪造缺失用量或结果。
7. **产品验收**：在可丢弃的目标副本上验证历史分页、工具详情、Replay、快照回读、统计、断线续读、重启与受控续聊，以及正常/兜底压缩中的原文还原、父快照选择和执行账本；使用确定性模型和工具夹具，绝不对真实历史自动重放副作用。
8. **独立性检查**：目标测试实例在源库不可访问时仍能读取全部迁移历史，不经旧库 fallback；测试不能修改正式只读验收目标。
9. **空间与增长检查**：按第 3.6 节逐分片报告最终主库、空闲页、页内利用率、索引/正文开销及 WAL 状态；把备份保留占用单列。固定负载在可丢弃副本上验证持续增长、长读事务释放、checkpoint 和离线整理，不为测试修改正式目标。所有冻结阈值通过或有预先定义的不适用依据，不能事后放宽阈值掩盖失败。

验证器应使用独立的源解码和目标读取路径，避免仅比较同一个有缺陷的转换函数两次输出。报告记录版本、实体计数、处理进度、摘要结果、失败数和验证平台，不包含正文或密钥。正式验收要求未转换记录为零、未解释差异为零；存在缺陷时保留证据并阻止切换。

### 5.6 整体切换与启用

- 仅在全部目标分片 verified 后，将完整目标集标记为可启用；逐片完成不等于允许逐片上线。
- 新运行时必须识别目标版本和完成标记，拒绝半迁移目标或新旧 generation 混合使用。通过启动流程和操作隔离禁止旧程序打开目标库，不能假定旧程序会识别并遵守新迁移标记。
- 采用可恢复的整体目录/manifest 切换协议，记录 prepared、verified、activated 等状态；具体实现需验证 Windows 文件占用与多文件切换中断，不能声称逐文件 rename 天然具备全局原子性。
- 切换期间保持服务停写。只读打开正式目标不会执行普通 Store 的恢复写入；开放业务写入后按正常服务语义处理中断状态，并与迁移数据转换区分。
- 保留旧 generation 和一致性备份，不自动删除。用户确认验收并明确保留策略之前，不做清理。

### 5.7 回退边界

- 切换前或目标尚未发生业务写入时，可在停止全部进程、核对切换状态后恢复旧 generation 与匹配的旧程序。
- 一旦新库已接受业务写入，直接切回旧库会丢失新记录，禁止自动回退；先保全两份数据，再人工决定修复或另行设计反向迁移。
- 不允许新旧库双写，也不通过恢复旧库重放工具来补齐新记录。

## 6. 实施阶段与完成门槛

1. 基线与夹具：记录事件循环延迟、排队、SQL、序列化、传输、内存与 WAL；覆盖长会话和多个分片，不预先承诺提速倍数。
2. 阻塞治理：异步 Store、单写入口、独立读通道、连接复用、索引和分片定位；保持事务、取消及未知结果边界。
3. Replay 改造：已提交输入缓存、目标检查点编码、按请求读取和兼容导出。
4. 消费者适配：HTTP/UI 分页、统计投影、恢复查询、正常/兜底压缩、Runtime IPC、上下文/快照读取；确认旧调用方不再隐式读取全部会话事件或同步写入。模型输入及快照材料仍按完整性要求读取，保持序列化匹配和顺序行为。
5. 完整迁移工具与验证器：冻结目标格式、空间配置和阈值，支持实际源版本，迁移所有旧数据及派生信息；完成顺序映射、序列化兼容、checkpoint 与离线整理流程，故障可恢复，但不允许边接业务写入边修改。
6. 副本演练及验收：确认覆盖、保真、独立读取、恢复与故障注入后，再由用户安排正式停写窗口，按第 5 节完成迁移和切换。

阶段开发可分别提交，但本次完整交付不能停在“新任务改好了、旧数据仍靠兼容”。正文去重/压缩若没有纳入已冻结目标版本，可以明确延期，不能以此延期为由漏迁已有材料。

## 7. 测试与可观察性

- 单元/回归覆盖 Unicode、大单条事件、数组顺序、JSON 扩展字段、源坏记录、ID/父链、提交回滚、Worker 故障、队列背压、连接关闭及重启。
- 迁移夹具覆盖旧 context、整条 Replay、增量 Replay、所有任务终态与未知状态、跨多个分片、同时间排序、空库、混合源版本及不存在捕获的 legacy。
- 顺序夹具使随机 ID、时间戳和源插入顺序不一致，覆盖 `rowid` 空洞、多个快照和多子任务；即使按 ID 比较的正文完全相同，最新快照或列表顺序改变也必须失败。验证备份顺序证据、目标续写和整理后的相同行为。
- 序列化夹具包含键顺序不同但 JSON 值相同的结果、嵌入 JSON 字符串、扩展字段、重复 call ID 和相同结果的多个候选；核对指纹、锚点恢复、精确工具匹配和 unknown。源锚点本就不适用时不伪造修复，迁移新增的不兼容必须失败。
- 压缩夹具覆盖所需事件落在 UI 最近页之外、祖先快照引用、跨批次歧义候选、部分失败和截断结果；正常与兜底压缩均对照全量参考路径验证，覆盖宿主及 Runtime IPC，不能因优化查询将已知与未知状态互换。
- 故障注入覆盖备份失败、磁盘不足、目标批次中断、提交后进度回执丢失、验证失败、源摘要变化、激活过程中断、旧程序误启动，以及业务写入后拒绝直接回退。
- HTTP/SSE/E2E 覆盖加载旧页期间的新事件、跨页工具关联、历史详情与统计、Replay 切换、关闭与重载；恢复不自动重放工具。
- 性能比较使用相同合成负载，覆盖一个、两个和四个任务并发加历史浏览，记录 p50/p95/p99、峰值内存与库/WAL 增长。先基线后设验收阈值。
- 空间治理夹具区分整页空闲、页内空洞、真实正文增长和重复载荷；覆盖长读事务阻碍 checkpoint、取消后释放、空闲期 WAL 回落、维护遇忙、磁盘不足及 VACUUM 中断。保持提交持久性配置一致，验证故障后的数据完整性和重新验收门禁；不能只看文件大小下降。
- 实现阶段按项目规则执行相关测试、`pnpm check`，UI/HTTP 变化再执行 `pnpm test:e2e`。Evaluation 仅由用户明确要求后手动运行，不纳入这些检查。
- 运行期接入 `src/tracing`，区分队列、查询、提交、编解码、Replay 重建及传输，记录开始、成功/失败/取消、耗时和安全关联 ID。
- checkpoint 与维护观测记录分片标识、队列等待、帧数、空间指标和结果，不记录正文；维护使用独立关联 ID，不伪装成历史任务执行。读事务超期、checkpoint 未完成和空间不足提供可诊断结果，不以无限重试阻塞业务。
- 离线迁移使用独立 migrationId 的安全阶段日志/trace，记录分片序号、实体数量、字节数与阶段结果，不写 SQL 参数、历史正文、工作区内容或凭据；不把迁移事件追加到历史任务 trace。
- Windows、Linux、macOS 的结论分别记录；单系统或模拟 Worker 通过不等于三平台迁移验收。

本次仅修改文档，因此不新增运行期 tracing，也不宣称执行了以上测试或真实迁移。
